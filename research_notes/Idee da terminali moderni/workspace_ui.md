# Workspace UI and architecture: Tabby, Waveterm (Wave), Electerm

Scope: concrete, transferable ideas for Oxterm (GTK3/VTE Rust: connections book, split panes, tabs, command palette, notes/monitor/log panels). Local baseline facts about Oxterm are cited from the working tree (read only): [Oxterm README](/home/andres/Progetti/oxterm/README.md), [Oxterm extensibility notes](/home/andres/Progetti/oxterm/docs/extensibility.md).

## 1. How do they structure workspaces, tabs, splits, profiles and persistent layouts?

### Takeaway
All three separate *layout persistence* from *connection/profile data*: Wave makes saved workspaces first-class named objects with icon/colour and persists their whole tab/widget tree; Electerm saves "workspace presets" made only of bookmark-origin tabs; Tabby leans on profile groups with a defaults cascade plus recoverable tabs. Oxterm already has declarative one/two-pane workspace JSON and a crash-resilient broker, so the main missing piece is a named, switchable workspace catalogue and a richer layout tree.

### Cited Findings
- Tabby is an Electron/Angular app; `tabby-core` provides "tabbed interface services, toolbar UI, config file management, hotkeys, tab recovery, logging, theming", with API surfaces `TabsService`, `SplitTabComponent`, `SplitContainer`, `TabRecoveryProvider`, `DockingService`, `BaseTabComponent`, `NewTabParameters` — [tabby-core API](https://docs.tabby.sh/); [HACKING.md](https://github.com/Eugeny/tabby/blob/master/HACKING.md).
- User-facing Tabby features: "multiple nested split panes", "tabs on any side of the window", an optional dockable global-hotkey "Quake console", "remembers your tabs", "custom shell profiles", progress detection and notification on process completion — [Tabby README](https://github.com/Eugeny/tabby).
- Tabby profiles are structured records with `id`, `name`, `type`, `group`, `icon`, `color`, `weight`, `options`, `terminalColorScheme`, `isBuiltin`, `isTemplate`, `behaviorOnSessionEnd`, `disableDynamicTitle`; groups form a tree (`buildGroupTree`, `resolveProfileGroupPath`), and defaults cascade global provider → group provider → profile (`getConfigProxyForProfile` with `skipGlobalDefaults` / `skipGroupDefaults`, `getProfileDefaults`, `setProviderDefaults`, `getProviderProfileGroupDefaults`) — [ProfilesService API](https://docs.tabby.sh/classes/ProfilesService.html).
- Tabby has a community `workspace-manager` plugin that "allows creating custom workspace profiles based on the given config", a `quick-cmds` plugin to send commands to one or all tabs, and `cctabs` for "named tabs for fleets of Claude Code and Codex CLI sessions, which you or Claude itself can open, read, prompt, fork and restore from the cctabs CLI" — [Tabby README](https://github.com/Eugeny/tabby).
- Wave workspaces: every window starts with an ephemeral workspace containing one tab with one terminal block; unsaved workspaces are deleted on window close except the last window, which is preserved; saved workspaces have editable name, icon and icon colour; the switcher shows which workspace is open in another window and focuses that window; switching away from an unsaved workspace offers "new window" vs replacing (and deleting) the current contents — [Wave Workspaces](https://docs.waveterm.dev/workspaces).
- Wave persistence boundary: "tabs, layouts, and terminal and AI histories of a saved workspace are persisted automatically", but unsaved editor/webpage changes are lost on close; commands in a previous tab keep running when switching tabs — [Wave Workspaces](https://docs.waveterm.dev/workspaces); [Wave Tabs](https://docs.waveterm.dev/tabs).
- Wave tabs can be pinned ("Pin Tab" via context menu), reordered by drag, switched with Cmd+1-9 / Cmd+[ / Cmd+]; each tab is a collection of widgets arranged as a tiled dashboard — [Wave Tabs](https://docs.waveterm.dev/tabs).
- Wave's layout is an n-tree emulating CSS Flexbox: nodes alternate tiling direction by level (row, column, row...), child size is a unitless ratio, automatic placement caps at 5 children per node then wraps, performance degrades past roughly 25 blocks, deleting a node re-minimises tree depth — [Wave Tabs, "Layout system under the hood"](https://docs.waveterm.dev/tabs).
- Wave drag/drop has 7 target zones per block (inline before/after, four out-of-line before/after inner/outer, and swap); resizing targets the containing node, with a guide line appearing after 500 ms; there is a "magnify" mode (Cmd+M) that pops one block in front of everything; gap size is `window:tilegapsize` — [Wave Tabs](https://docs.waveterm.dev/tabs).
- Wave global keybindings include Cmd+D / Cmd+Shift+D for right/below splits, `Ctrl+Shift+s` + arrow chords for directional splits, `Ctrl+Shift` to show block numbers, `Ctrl+Shift+1-9` to switch blocks, `Ctrl+Shift+Arrows`/hjkl to move between blocks, Cmd+Ctrl+1-9 to switch workspaces — [Wave Key Bindings](https://docs.waveterm.dev/keybindings).
- Wave durable sessions (v0.14) use a three-level config hierarchy block > connection > global (`term:durable`), are opt-in for SSH only, buffer output while detached and survive restarts/network changes — [Wave Durable Sessions](https://docs.waveterm.dev/durable-sessions).
- Electerm workspaces are named presets: set up a layout (single, 2 columns, 2x2 grid, etc.), open tabs, then "Save Workspace" (new or overwrite); loading a workspace **closes all current tabs** and restores the saved set; only tabs opened from bookmarks are saved (temporary tabs are excluded); workspaces can also be managed in Settings → Workspace — [Electerm Workspace Feature](https://github.com/electerm/electerm/wiki/Workspace-Feature).
- Electerm also documents "quick connect" and "Default Profile" pages in its wiki index — [Electerm wiki](https://github.com/electerm/electerm/wiki).
- Oxterm baseline: tmux-style single/vertical/horizontal splits with `Ctrl+B` prefix; reorder/rename/detach tabs and adopt running tabs across windows; persistent display-free broker keeping shells alive across GUI crashes, with local/remote attach/detach; declarative `oxterm workspace FILE` with `single`/`vertical`/`horizontal` layout, tabs containing `title`, `cwd`, `command`, `color`, and `--new-window` for a clean window — [Oxterm README](/home/andres/Progetti/oxterm/README.md); [Oxterm extensibility](/home/andres/Progetti/oxterm/docs/extensibility.md).

### Inferences
- **Highest-value addition:** a workspace *catalogue* (named, icon/colour-tagged saved layouts) layered on Oxterm's existing JSON workspace spec, with "unsaved workspace" semantics and a switcher. This is mostly persistence/UI work, not a new layout engine.
- Wave's flexbox-like n-tree is a natural evolution of Oxterm's current 1-or-2-pane JSON layout: store nodes as `{orientation, weight, children|pane}` and reuse GTK `GtkPaned` recursively. Unitless weights are easy to serialise into the existing workspace file.
- Wave's 7 drop zones and swap are a UX refinement, but a simpler first step is drag-to-split with a visible drop preview; the "25 blocks" caution suggests bounding complexity.
- Tabby's profile-group defaults cascade maps directly onto Oxterm's existing `--profile NAME` (currently "session only") plus the connections book: define profile → group → global layers so a bookmark can inherit theme/font/env, and keep per-connection overrides winning.
- Electerm's rule "only bookmark-origin tabs are saved in a workspace" is a pragmatic way to avoid storing ephemeral/secrets-bearing command lines in workspace files — worth copying for Oxterm's workspace serialisation.
- Oxterm's broker already covers Wave's "durable sessions" idea locally; Wave's additional lesson is a *visible session state indicator* (attached/detached/awaiting) rather than new machinery.

### Gaps
- The Wave `/layout` documentation page returned only navigation (no body) in the fetched HTML, so the exact schema of `window:tilegapsize` and any further layout config are unverified — [Wave layout page](https://docs.waveterm.dev/layout).
- `tabby.sh/docs/` returned no content; the detailed Tabby user docs on layouts/workspaces were not retrievable, so claims about Tabby workspace persistence rely on the README and community plugin list.
- No reliable documentation was found for Electerm's profile hierarchy beyond the "Default Profile" wiki title; whether Electerm profiles inherit settings like Tabby groups is unknown.
- Web search was unavailable (HTTP 402) during this research, so release-note-level details (e.g. when each workspace feature shipped) were not collected except where explicitly version-badged in Wave docs.

## 2. What plugin/extension architecture do they use, and what problems does it solve?

### Takeaway
Tabby solves "one app, many shells/protocols/platforms" with Angular dependency-injection plugins (even the terminal, settings and Electron backend are plugins). Wave and Electerm instead use *declarative recipes*: JSON widget definitions and folder-based widgets with a narrow, capability-gated API. Oxterm deliberately removed arbitrary external plugins; its control API, triggers, events and `extensions.json` already deliver most of the benefit safely, and declarative "panel recipes" are the natural next step.

### Cited Findings
- Tabby plugins are Angular `NgModule` default exports injected into the app's root module; they contribute via singular or multi DI providers such as `ToolbarButtonProvider`, `TabContextMenuItemProvider`, `HotkeyProvider`, `ProfileProvider`, `ConnectableProfileProvider`, `QuickConnectProfileProvider`, `ConfigProvider`, `FileProvider`, `ThemesService`, `TabRecoveryProvider` — [HACKING.md](https://github.com/Eugeny/tabby/blob/master/HACKING.md); [tabby-core API](https://docs.tabby.sh/).
- Tabby loads plugins from the source checkout in dev mode, the user plugins directory, and `TABBY_PLUGINS`; only packages with the `tabby-plugin` keyword load; publishing to npm with that keyword makes them appear in the in-app Plugin Manager — [HACKING.md](https://github.com/Eugeny/tabby/blob/master/HACKING.md).
- The Tabby repo itself is split into plugin packages: `tabby-core` (base UI/tabs), `tabby-electron`, `tabby-web`, `tabby-local` (shells/profiles), `tabby-terminal`, `tabby-settings`, `tabby-plugin-manager`, `tabby-ssh`, `tabby-serial`, `tabby-telnet`, `tabby-linkifier`, `tabby-community-color-schemes` — [HACKING.md](https://github.com/Eugeny/tabby/blob/master/HACKING.md); [repo tree](https://github.com/Eugeny/tabby).
- Tabby's plugin ecosystem directly supplies features the core doesn't have: Docker connections, title control, quick commands, save-output, config sync to Gist/Gitee, workspace-manager, SFTP tab, background images, keyword highlight, web-auth handler, MCP server, SSH key-name mapping, serial timestamps, named AI coding-agent tabs — [Tabby README](https://github.com/Eugeny/tabby).
- Tabby core exposes `VaultService` with `enable/disable`, `load/save`, `encrypt/decrypt`, `getPassphrase/forgetPassphrase`, `getSecret/addSecret/updateSecret/removeSecret` keyed by `(type, key)` — an encrypted container primitive available to plugins — [VaultService API](https://docs.tabby.sh/classes/VaultService.html).
- Wave's extensibility is declarative: `<WAVETERM_HOME>/config/widgets.json` entries have `icon`, `label`, `color`, `display:order`, `description`, `magnified` and a `blockdef.meta` describing `view` (`term`, `web`, `sysinfo`), `controller` (`cmd` vs persistent `shell`), `cmd`, `cmd:args`, `cmd:shell`, `cmd:cwd`, `cmd:env`, `cmd:runonstart`, `cmd:runonce`, `cmd:clearonstart`, `cmd:closeonexit` (+force/delay), `cmd:nowsh`, `cmd:jwt`, per-shell `cmd:initscript.*`, and `connection` for remote shells — [Wave Custom Widgets](https://docs.waveterm.dev/customwidgets).
- Wave ships five default widgets (`defwidget@terminal`, `@files`, `@web`, `@ai`, `@sysinfo`) that can be overridden or removed by setting the key to `null` — [Wave Custom Widgets](https://docs.waveterm.dev/customwidgets).
- Wave's `wsh` CLI is a second extension surface: it can open web/preview blocks, run isolated command blocks (`wsh run -x`), set/get variables in block/tab/workspace/global scopes, and pipe output/files to AI — [Wave wsh overview](https://docs.waveterm.dev/wsh).
- Electerm user widgets are plain folders with `package.json` under `<data dir>/widgets/<id>/`, importable from a folder or GitHub/AtomGit URL (copy, never symlink; validation before copy; no `npm install`, dependencies must be vendored) — [Electerm User widget guide](https://github.com/electerm/electerm/wiki/User-widget-guide).
- Electerm widget shapes: **style** (only `electerm.styles`, no JS), **script/instance** (`run` / `widgetRun` with `start`/`stop` lifecycle, logs, `singleInstance`, `autoRun`), **config mode** (host-generated form from `electerm.configs` with string/textarea/number/boolean/password/file/directory/select fields), and **own UI** (sandboxed iframe at `electerm-widget://<id>/`, different origin, fixed JSON request/response bridge, no push events) — [Electerm User widget guide](https://github.com/electerm/electerm/wiki/User-widget-guide).
- Electerm's widget API (`require('@electerm/widget-api')`) is capability-gated (`css`, `notify`, `openExternal`, `clipboard`, `dialog`, `secret`, `net`), written into the widget's own `node_modules` by the host; a require guard allows Node built-ins and own-folder files but refuses `electron` and paths outside the widget; the guide explicitly calls it "a platform boundary, not a sandbox" — [Electerm User widget guide](https://github.com/electerm/electerm/wiki/User-widget-guide).
- Electerm security details: password fields are never persisted even when `persist` is on; CSS belongs to a running instance and disappears on stop; tabs opened by a widget are tagged `from: widget:<id>` and never written to connection history so decrypted credentials stay out of synced data — [Electerm User widget guide](https://github.com/electerm/electerm/wiki/User-widget-guide).
- Oxterm baseline: external plugin packages, plugin manager, plugin menu and WASM panel runtime were **removed** because "the model could not draw UI" and the menu confused users; supported surfaces today are the control API (`new`, `split`, `send`, `capture`, `wait`), `events`, `actions`, `triggers.json`, declarative workspaces, `extensions.json` status widgets and palette entries, and `oxterm mcp`; deferred items include context-menu contributions, hot reload and a WASM panel runtime; the file browser is core — [Oxterm extensibility](/home/andres/Progetti/oxterm/docs/extensibility.md).

### Inferences
- Oxterm's situation resembles Wave's more than Tabby's: the existing binary already has a stable, display-free control socket and declarative JSON surfaces, so adding *data-driven* recipes (monitor/log/notes panel definitions, status widgets, palette rows) avoids the failure mode that killed the old plugin host.
- Wave's `blockdef.meta` fields are almost exactly what an Oxterm "panel recipe" needs: a view type, a command, cwd/env, run-on-start, clear-on-start, close-on-exit, and a connection reference. These can be validated in `src/headless/` and fit the existing boundary test.
- Electerm's widget lessons worth stealing even without plugins: (a) manifest validation *before* installation, (b) capabilities instead of version checks, (c) secrets never persisted by declarative config, (d) lifecycle-owned styling/state, (e) provenance tagging of automation-created tabs so credentials never leak into synced history.
- Tabby's DI model solves cross-platform backend swapping (Electron vs web, local vs SSH/serial); in a single-platform GTK app this complexity buys little. Keep the problem statement but not the mechanism: define small trait-based providers for shell/connection types instead of a runtime DI container.
- A safe intermediate between "no plugins" and "arbitrary code": allow declarative recipes plus a small, explicit action vocabulary (already present: notify, insert-text, open-url, set-tab-title/color), and refuse arbitrary shell commands from untrusted config — Oxterm already does this in triggers/actions.

### Gaps
- No documentation was found on how Tabby's `TabRecoveryProvider` serialises recovery tokens or whether layouts (splits) are recovered, only that tab recovery is an advertised core service — [tabby-core API](https://docs.tabby.sh/).
- Wave's docs describe custom widgets as JSON only; whether third-party widgets can ship executable code outside `wsh` scripts is not documented — [Wave Custom Widgets](https://docs.waveterm.dev/customwidgets).
- Oxterm's removed external plugin host exists in Git history (`bceb0a2` and later) but was not inspected here; reasons beyond "could not draw UI / confusing menu" are unknown — [Oxterm extensibility](/home/andres/Progetti/oxterm/docs/extensibility.md).

## 3. Which UX details stand out (command palette, prompt recipes, AI panels, remote browsing, transfer queues, themes, keybindings, settings UI)?

### Takeaway
The strongest transferable patterns are: Electerm's *multi-step quick commands* (with wait-for-output and guarded recording), Wave's *uniform block model* with preview/process/sysinfo panels plus `wsh` as a CLI into the GUI, and Tabby's *fully configurable multi-chord keybindings*. Oxterm already has a fuzzy palette, snippets, an ACP agent pane and a two-pane SFTP browser; the gaps are step-based recipes, richer block types, and visible state/provenance affordances.

### Cited Findings
- **Command palette / launcher.** Oxterm has `Ctrl+Shift+P` fuzzy search over actions, settings and slash commands, and `extensions.json` can add extra palette rows (run in a new tab) — [Oxterm README](/home/andres/Progetti/oxterm/README.md); [Oxterm extensibility](/home/andres/Progetti/oxterm/docs/extensibility.md). Tabby exposes `CommandService`, `CommandProvider`, `CommandLocation` and `SelectorService` as extension points — [tabby-core API](https://docs.tabby.sh/). Wave has a replaceable "launcher" block (`Ctrl+Shift+x`) and `app:defaultnewblock` setting — [Wave Key Bindings](https://docs.waveterm.dev/keybindings).
- **Prompt recipes.** Electerm quick commands are a name + ordered steps + labels + optional shortcut; step types are `command` (optional Enter, multi-line allowed), `key` (named key, repeat 1–100), `wait for text` (plain case-insensitive, escape codes stripped, only output after previous step counts, timeout default 10 s / 0 = forever), `ask for input` (optional hidden/password field, answer typed at that step and not stored), and a per-step delay before execution (default 100 ms) — [Electerm quick commands](https://github.com/electerm/electerm/wiki/quick-commands).
- Electerm quick-command panel UX: `Q` button in terminal footer, floating box that can be pinned or docked, search across names and every step's text, label filter, sort-by-frequency (remembered), label grouping with remembered collapse state, drag reorder disabled while sorted/grouped, hover preview of steps, and a footer chip shown only for runs >0.5 s with progress `3/7` and `+N` for concurrent runs; runs are bound to their tab and stop when it closes — [Electerm quick commands](https://github.com/electerm/electerm/wiki/quick-commands).
- Electerm recording captures typed text, pastes and keys, turns Enter into command steps, coalesces repeated keys, drops unknown escape sequences (e.g. cursor-position reports), warns at start that passwords are captured and saved/synced, and opens the filled form for review under label `recorded`; `{{time}}`, `{{date}}`, `{{clipboard}}` expand when the step is sent — [Electerm quick commands](https://github.com/electerm/electerm/wiki/quick-commands).
- Electerm distinguishes a quick-command "wait for text" step (blocks one run, plain text, timeout) from Settings → Triggers (beta: always-on regex rules, text or regex, actions send text or notify, repeat every match / with cooldown / once per session, no timeout) — [Electerm quick commands](https://github.com/electerm/electerm/wiki/quick-commands).
- Oxterm's current recipe primitive is much simpler: `/snippet add NAME CMD` saves a parameterised snippet and `/snippet NAME [ARGS...]` expands it into the shell prompt; triggers are regex→action rules limited to profiles and OSC 133 command output and never execute code — [Oxterm README](/home/andres/Progetti/oxterm/README.md); [Oxterm extensibility](/home/andres/Progetti/oxterm/docs/extensibility.md).
- **AI panels.** Wave AI is a toggleable panel (`Cmd+Shift+a`) with a "Widget Context" switch: ON lets the AI read terminal scrollback, capture widget screenshots, list/read files (approval required), write files with diff preview + approval, navigate web widgets and call custom widget tools; OFF is plain chat with attached files. Attachments: images 10 MB, PDFs 5 MB, text/code 200 KB; `wsh ai` pipes stdin or attaches files with `-m` message, `-s` submit, `-n` new chat; BYOK/local models via OpenAI-compatible providers — [Wave AI](https://docs.waveterm.dev/waveai).
- Wave's AI feature list explicitly marks "remote file access" and "command execution (with approval)" as *coming soon*, i.e. not current behaviour — [Wave AI](https://docs.waveterm.dev/waveai).
- Tabby has a community `mcp-server` plugin and `cctabs` plugin for named Claude Code / Codex CLI agent tabs — [Tabby README](https://github.com/Eugeny/tabby). Electerm advertises multi-format LLM integration (OpenAI Chat Completions, OpenAI Responses, Anthropic Messages), command suggestions/script writing/explaining selections, bookmark/theme creation, agent mode for terminal operations, and an MCP widget — [Electerm README](https://github.com/electerm/electerm).
- Oxterm baseline: opt-in ACP agent pane (`Ctrl+Shift+.`) with per-tab session persistence, `?prompt` shell syntax, `oxterm fix` sending failed command output/directory/status, and an MCP server with audit log and fine-grained permission policies — [Oxterm README](/home/andres/Progetti/oxterm/README.md).
- **Remote browsing / previews.** Wave's `preview` widget renders directories (Finder-like `ls -alh` view with substring filter, sortable columns, hidden-file toggle, refresh, common-folder menu), markdown, images and videos; `codeedit` uses a Monaco editor with Cmd+E edit, Cmd+S save, Cmd+R revert; two directory widgets allow drag-copy of files/folders **across connections**; a Process Viewer (v0.14.5) shows sortable PID/command/CPU/memory (plus status/threads on Linux), sends Unix signals from a row context menu, filters with Cmd+F and pauses with Space — [Wave Widgets](https://docs.waveterm.dev/widgets).
- Wave bridges local and remote files with `wsh file` and the `wsh://local/~/` (or `~/`) prefix, so a remote terminal can read/append/copy local files; `wsh view` opens preview blocks, `wsh edit` opens the editor, `wsh web open` opens web blocks — [Wave wsh overview](https://docs.waveterm.dev/wsh).
- Electerm supports double-click editing of small remote files, SFTP following terminal cwd, Zmodem (rz/sz) and Trzsz, tunnels/connection hopping, X11 and global/session proxy — [Electerm README](https://github.com/electerm/electerm); [Electerm wiki](https://github.com/electerm/electerm/wiki). Tabby supports Zmodem transfer and has a community `sftp-tab` plugin; its core API exposes `FileTransfer`, `FileUpload`, `FileDownload`, `DirectoryUpload`, `DirectoryDownload` — [Tabby README](https://github.com/Eugeny/tabby); [tabby-core API](https://docs.tabby.sh/).
- Oxterm baseline: built-in two-pane SFTP/FTP browser with drag-and-drop, remote file editing (upload on save) and directory synchronisation, plus SSH/Mosh/Telnet/Serial/Docker/Kubernetes/AWS SSM/RDP/VNC/SPICE connection picker — [Oxterm README](/home/andres/Progetti/oxterm/README.md).
- **Themes.** Wave supports tab themes, terminal styles and background images, and lets each connection override `term:theme`, `term:fontsize`, `term:fontfamily` (block metadata wins over connection settings) — [Wave README](https://github.com/wavetermdev/waveterm); [Wave Connections](https://docs.waveterm.dev/connections). Electerm has a dedicated theme site, custom CSS examples, and style-only user widgets whose CSS is tied to a running instance — [Electerm README](https://github.com/electerm/electerm); [Electerm User widget guide](https://github.com/electerm/electerm/wiki/User-widget-guide). Oxterm ships 247 built-in themes, Ghostty/iTerm2 `.itermcolors` import and automatic light/dark switching — [Oxterm README](/home/andres/Progetti/oxterm/README.md).
- **Keybindings.** Tabby advertises "fully configurable shortcuts and multi-chord shortcuts"; its `HotkeysService` tracks pressed keys/keystrokes, partial matches (`matchActiveHotkey(partial)`), key release (`hotkeyOff$`), and enable/disable levels — [Tabby README](https://github.com/Eugeny/tabby); [HotkeysService API](https://docs.tabby.sh/classes/HotkeysService.html). Wave chords give 2 seconds for the second key and make Escape after a chord prefix a no-op; keybindings are documented in per-widget sections (global, preview, web, AI, terminal, process viewer) — [Wave Key Bindings](https://docs.waveterm.dev/keybindings). Electerm lets quick commands bind their own shortcut, checks these *before* built-ins, and warns in the shortcut editor when keys are already taken — [Electerm quick commands](https://github.com/electerm/electerm/wiki/quick-commands).
- **Settings UI.** Tabby's settings tab and plugin manager are themselves plugins, and plugins contribute configuration via `ConfigProvider`/`ProfileSettingsComponent` — [HACKING.md](https://github.com/Eugeny/tabby/blob/master/HACKING.md); [tabby-core API](https://docs.tabby.sh/). Electerm generates settings forms from a manifest with explicit field types and drops unknown keys — [Electerm User widget guide](https://github.com/electerm/electerm/wiki/User-widget-guide). Oxterm's CLI help/man page/completions/settings docs are generated from `src/headless/spec.rs` — [AGENTS.md](/home/andres/Progetti/oxterm/AGENTS.md).
- **Notable small affordances:** Tabby warns on multiline paste and detects progress/process completion; Wave shows block numbers while holding Ctrl+Shift and has a "refocus current block" key; Electerm's quick-command chip stays hidden for sub-half-second runs and its panel remembers sort/group preferences — [Tabby README](https://github.com/Eugeny/tabby); [Wave Key Bindings](https://docs.waveterm.dev/keybindings); [Electerm quick commands](https://github.com/electerm/electerm/wiki/quick-commands).

### Inferences
- The most concrete Oxterm feature gap is a **step engine**: Oxterm's `/snippet` is one command; Electerm's steps (`send`, `key`, `wait-for-output`, `ask`, `delay`) can be implemented entirely with the existing control API (`oxterm send`, `events --output`, `capture`, `wait`) and OSC 133 boundaries. Add an explicit "no password recording" default to avoid Electerm's documented secret-leak risk.
- Wave's uniform block model suggests letting Oxterm's notes/monitor/log panels behave like panes: same header menu, focus border, magnify, close, and drag-to-layout. Process-viewer-like panels are feasible via `/proc` sampling; markdown/image/PDF preview is not (see section 4).
- Wave's "widget context" toggle is a good pattern for Oxterm's ACP pane: one explicit switch controlling whether the agent may read scrollback/files, with approval prompts and an audit trail — Oxterm already has MCP audit/permissions to build on.
- Per-connection theme/font overrides are cheap to add to Oxterm's connections book and are more useful than yet more global themes.
- A chord engine with conflict detection is feasible: Oxterm already has a `Ctrl+B` prefix, so generalising to user-defined chords and warning on collisions (Electerm's shortcut editor) is incremental.

### Gaps
- No dedicated documentation on a visual **transfer queue** was found for any of the three projects. Evidence is indirect: Wave `wsh file cp`, Tabby core `FileTransfer`/`DirectoryUpload` classes, Electerm Zmodem/Trzsz support; whether any has a first-class progress/cancel queue UI is unverified — [Wave wsh](https://docs.waveterm.dev/wsh); [tabby-core API](https://docs.tabby.sh/); [Electerm README](https://github.com/electerm/electerm).
- Electerm's AI model config and "agent mode" details were not fetched (wiki page exists but was not read) — [Electerm AI model config guide](https://github.com/electerm/electerm/wiki/AI-model-config-guide).
- Tabby's docs site (`tabby.sh/docs`) returned no content, so details of its settings UI and keybinding editor remain inferred from the API surface and README.

## 4. Which ideas are feasible in a GTK3 Rust app, and which depend on Electron/web tech?

### Takeaway
Declarative layout trees, workspace catalogues, step recipes, CLI-to-GUI control, named secrets via libsecret, keyring-backed credential references and small monitor panels all fit Oxterm's GTK3/VTE architecture. Embedded web widgets, sandboxed HTML widget UIs, Monaco-style editing and app-wide CSS theming are Electron/web-app features that should be replaced with native equivalents or skipped.

### Cited Findings
- Oxterm is a native GTK3 + VTE Rust application; its headless/broker logic is deliberately display-free and guarded by a boundary test, and external processes cannot draw UI inside it — [Oxterm README](/home/andres/Progetti/oxterm/README.md); [Oxterm extensibility](/home/andres/Progetti/oxterm/docs/extensibility.md); [AGENTS.md](/home/andres/Progetti/oxterm/AGENTS.md).
- Oxterm's control surface is already CLI/JSON-RPC based: `oxterm new/split/send/capture/wait`, `events` stream, `action`, workspace files, status widgets and palette entries, `oxterm mcp` — [Oxterm extensibility](/home/andres/Progetti/oxterm/docs/extensibility.md).
- Tabby is explicitly an Electron app with an Angular/TypeScript frontend built by Webpack — [HACKING.md](https://github.com/Eugeny/tabby/blob/master/HACKING.md). Wave's repository contains `electron.vite.config.ts` and `electron-builder.config.cjs`, and its custom web widgets are just a `view: "web"` + URL in JSON — [Wave repo](https://github.com/wavetermdev/waveterm); [Wave Custom Widgets](https://docs.waveterm.dev/customwidgets). Electerm is developed with Electron tooling (`electron-builder`, Vite dev server) — [Electerm README](https://github.com/electerm/electerm).
- Wave's Codeedit widget is a Monaco editor and its markdown/PDF/video previews and web widgets are browser-rendered; these are tied to the web frontend — [Wave Widgets](https://docs.waveterm.dev/widgets); [Wave Custom Widgets](https://docs.waveterm.dev/customwidgets).

This demonstrates a pattern that does not require GUI web tech.
- Oxterm's GTK side already depends on GtkSourceView 4 (per build instructions) and has 247 themes plus Ghostty/iTerm2 import — [Oxterm README](/home/andres/Progetti/oxterm/README.md).

### Inferences
- **Feasible natively (high confidence):** named workspaces + icon/colour switcher; recursive paned layouts with weights and drag-to-split/magnify; pinned tabs; profile/group defaults cascade; connection-level theme/font overrides; a block/pane header menu with focus/magnify/close; process/sysinfo monitor panels (sample `/proc`, render in `GtkTreeView`/drawing area); notes/log panels (already present); declarative panel recipes validated in `src/headless/`; step-based quick commands and recording built on `send`/`events`; workspace/tab/global variable scopes via a JSON store; chorded keybindings with conflict detection; named secrets through libsecret; deep links (`ssh://user@host`) routed into the connections book.
- **Feasible with extra work:** durable *remote* sessions in the Wave sense require shipping and installing a small helper binary on the SSH host (Wave uses Go); Oxterm's local broker does not cross the network. Zmodem/Trzsz can be delegated to external binaries but need terminal passthrough coordination. Rich text/preview panes can be approximated with GtkSourceView for code/markdown source, not rendered output.
- **Electron/web-dependent or poor fit:** embedded web/browser widgets (needs WebKitGTK/CEF, heavy); Monaco editor (use GtkSourceView); HTML widget UIs in sandboxed iframes (no GTK equivalent; a WASM panel runtime was explicitly deferred by Oxterm); app-wide CSS injection/style widgets (GTK CSS providers are narrower and theme-driven); arbitrary Node/DI plugins (explicitly rejected in Oxterm). BYOK cloud AI is feasible over HTTP but needs credential storage and careful consent UX.
- The "capability-gated API" idea from Electerm still applies to native code if a future extension surface is added: declare what a component may do (notify, clipboard, file access) rather than assuming full process privileges.

## 5. How do they handle connection management, credentials and sync?

### Takeaway
Wave and Oxterm share the "native keychain + named secret references" model; Electerm adds configurable cross-device sync of bookmarks/themes/recipes with explicit direction and schedule, plus careful provenance rules so synced data never contains decrypted credentials; Tabby offers an encrypted passphrase-protected vault and a plugin pattern for key-name remapping. Oxterm already has keyring prompts and safety badges, but no documented named-secret store, cross-device sync or provenance tagging.

### Cited Findings
- Wave secrets (v0.13) are stored encrypted in native keychains: macOS Keychain, Windows Credential Manager, Linux Secret Service (GNOME Keyring/KWallet required). Names must match `^[A-Za-z][A-Za-z0-9_]*$`; UI via `wsh secret ui` or settings icon; CLI `wsh secret list/get/set/delete`; connections reference them via `ssh:passwordsecretname` in `connections.json`, so the password isn't stored in config — [Wave Secrets](https://docs.waveterm.dev/secrets).
- Wave connection dropdown merges `connections.json` with `~/.ssh/config` and `/etc/ssh/ssh_config`; manually typed or `wsh ssh` connections are added on first successful connect; supported SSH config keys include Host/User/HostName/Port/IdentityFile/BatchMode/PubkeyAuthentication/PasswordAuthentication/KbdInteractiveAuthentication/PreferredAuthentications/AddKeysToAgent/IdentityAgent/IdentitiesOnly/ProxyJump/UserKnownHostsFile/GlobalKnownHostsFile, with `Match` incompatible — [Wave Connections](https://docs.waveterm.dev/connections).
- Wave connection metadata includes `display:hidden`, `display:order`, per-connection `term:theme`/font overrides, `cmd:env` and per-shell `cmd:initscript.*`, `ssh:identityfile` lists, `ssh:addkeystoagent`, `ssh:proxyjump`, `ssh:passwordsecretname`, and `conn:wshenabled` / `conn:askbeforewshinstall` controlling remote helper installation; agent resolution uses `ssh:identityagent`, else Windows OpenSSH pipe, else `SSH_AUTH_SOCK` — [Wave Connections](https://docs.waveterm.dev/connections).
- Wave durable sessions keep state on the remote host, transmit only over the existing SSH connection, open no remote ports, buffer output remotely while disconnected, and clean up orphaned sessions on reconnect; each session runs a lightweight Go process on the server — [Wave Durable Sessions](https://docs.waveterm.dev/durable-sessions).
- Tabby's SSH client features X11/port forwarding, jump hosts, agent forwarding (Pageant and native agents), and login scripts; it ships an "integrated encrypted container for SSH secrets and configuration" — [Tabby README](https://github.com/Eugeny/tabby).
- Tabby's `VaultService` is an enable/disable-able encrypted store with passphrase handling (`getPassphrase`, `forgetPassphrase`), `encrypt`/`decrypt`, and secrets keyed by `(type, key)` — [VaultService API](https://docs.tabby.sh/classes/VaultService.html).
- Tabby ecosystem patterns for multi-machine setups: `sync-config` plugin syncs config to Gist or Gitee; `ssh-keymap` lets *synced* SSH profiles reference private keys by name while a local, never-synced mapping file holds the real paths; `web-auth-handler` supports in-app browser auth popups (built for Warpgate) — [Tabby README](https://github.com/Eugeny/tabby).
- Electerm syncs bookmarks, themes and quick commands to GitHub/Gitee secret gist, WebDAV, a custom server or Electerm cloud; Auto Sync supports "On Change" (default) or 5/10/15/30-minute and 1/2/6/12/24-hour intervals, with an explicit `Upload` (default) or `Download` direction — [Electerm README](https://github.com/electerm/electerm); [Electerm Auto data Sync](https://github.com/electerm/electerm/wiki/Auto-data-Sync).
- Electerm auth support: publicKey, password, ssh agent, certificates, OTP, NetBird; SSH tunnels and connection hopping; deep links such as `ssh://user@host:22` — [Electerm README](https://github.com/electerm/electerm). Its wiki has pages for SSH agent, certificate auth, key-content-vs-key-path, proxy format and personal access tokens — [Electerm wiki](https://github.com/electerm/electerm/wiki).
- Electerm credentials in widgets: a widget can declare `electerm.credentialProvider` with `get`/`save` exports to serve Passbolt-style vaults to bookmark forms; only bookmarks with `usePasswordManager` and no stored password are passed; config values are stored in encrypted local storage, `password` fields never; tabs opened by widgets are excluded from connection history "so decrypted credentials stay out of synced data" — [Electerm User widget guide](https://github.com/electerm/electerm/wiki/User-widget-guide).
- Oxterm baseline: a separate `oxterm-askpass` binary provides keyring password prompts; the connections panel warns/badges production hosts, active SSH tunnels and `ForwardAgent yes`; command history lives in SQLite and notes in Markdown with FTS5; the control socket is user-private (0700 dir, 0600 socket, `SO_PEERCRED`) and never listens on the network; event subscribers that are too slow are disconnected; triggers cannot read/modify the input line so they cannot intercept passwords — [Oxterm README](/home/andres/Progetti/oxterm/README.md); [Oxterm extensibility](/home/andres/Progetti/oxterm/docs/extensibility.md).

### Inferences
- Oxterm's askpass/keyring setup maps cleanly onto Wave's named secrets: add `oxterm secret list/get/set/delete` backed by libsecret and let a connection reference a secret name instead of embedding a password. This also gives the ACP agent and recipes a safe way to consume credentials without printing them.
- Electerm's two sync decisions are worth copying verbatim: (1) explicit **direction** and **schedule** rather than silent bidirectional merge, (2) exclusion of automation-derived sessions from synced history. Oxterm can tag tabs created by recipes/MCP/ACP with provenance and keep them out of any future sync set.
- Tabby's `ssh-keymap` pattern solves a real conflict: profile data may be synced while machine-local paths must not be. If Oxterm adds config sync, split "portable fields" (host, user, port, tags, colour) from "local fields" (identity file paths, key references, proxy sockets).
- Wave's `display:hidden` / `display:order`, per-connection font/theme, agent resolution order and `cmd:env`/init scripts are all low-cost metadata fields for Oxterm's connection book. The `ProxyJump`/known-hosts subset is a useful checklist for the SSH backend.
- Durable remote sessions are the one credential-adjacent idea that would need significant new infrastructure (remote helper deployment); Oxterm's local broker already covers crash/detach resilience without it.
