# Idee da terminali moderni: rendering (WezTerm, Rio, Contour, notcurses)

Scope: actionable lessons for Oxterm (GTK3 + `zoha-vte` / VTE 0.70, Rust). Research date 2026-11-27. Web search was unavailable (HTTP 402), so findings come from primary docs fetched directly. Local Oxterm facts are cited with local file paths.

## 1. What rendering architecture does each use (GPU vs CPU, custom emulator vs library) and what does that enable?

### Takeaway
All three terminal emulators own both the VT state machine and the renderer, and all three separate them into layers (headless terminal core + replaceable rasterizer), which is what enables GPU rendering, alternate frontends, embeddable libraries and headless tests. notcurses is the opposite kind of project: a TUI client library that renders *into* a terminal via escape sequences and terminfo, not an emulator. Oxterm delegates both state and pixels to VTE, so it can only copy the *interaction/protocol* ideas without replacing VTE; pixel-level ideas require a new renderer.

### Cited Findings
- WezTerm is a "GPU-accelerated cross-platform terminal emulator and multiplexer" written in Rust; it ships three render frontends: `OpenGL` (GPU rasterization), `Software` (CPU rasterization) and `WebGpu`, with WebGPU backends Metal (macOS), Vulkan and DirectX 12; the default was briefly WebGpu and then reverted to OpenGL, and WezTerm auto-selects `Software` under Windows Remote Desktop. — [README](https://github.com/wezterm/wezterm/blob/main/README.md); [front_end config](https://wezterm.org/config/lua/config/front_end.html)
- WezTerm's multiplexer is built on *domains* (local, unix socket, SSH, TLS): a remote daemon hosts tabs/panes and the local GUI attaches, giving native mouse, clipboard and scrollback on top of remote sessions. — [Multiplexing docs](https://wezterm.org/multiplexing.html)
- Rio is a Rust workspace split into `librio` (terminal state, VT parser, pull API for cells, C ABI), `rio-vt`, `rio-grid`, `rio-graphics`, `rio-fonts`, `rio-grapheme-width`, `teletypewriter` (PTY), `sugarloaf` (renderer) and `libsugarloaf` (C ABI over the renderer); MSRV is 1.100.0. — [Cargo.toml](https://github.com/raphamorim/rio/blob/main/Cargo.toml); [repo root listing](https://api.github.com/repos/raphamorim/rio/contents/)
- Rio's `sugarloaf` renderer is WebGPU-based (also targets WASM); on Linux the native Vulkan backend compiles GLSL shaders to SPIR-V at build time (needs `glslang-tools`/`glslc`), while on macOS `libsugarloaf` attaches a `CAMetalLayer` and uses native Metal. The host rasterizes glyphs and builds flat cell arrays; sugarloaf owns the glyph atlas and GPU compositing. — [sugarloaf README](https://github.com/raphamorim/rio/blob/main/sugarloaf/README.md); [libsugarloaf README](https://github.com/raphamorim/rio/blob/main/libsugarloaf/README.md)
- Contour is C++23 with an explicit dependency-ordered layer stack: `crispy` → `coro` → `net` → `text_shaper`/`vtparser` → `vtpty` → `vtbackend` (headless terminal emulation) → `vtrasterizer`/`vtworkspace` → `vthost` (Qt-free session daemon + protocols) → `contour` (GUI). `vtrasterizer` is target-independent: the caller decides how pixels are stored/rendered. The main thread handles input and display; a dedicated thread per PTY reads output and updates terminal state. — [internals index](https://github.com/contour-terminal/contour/blob/master/docs/internals/index.md)
- Contour renders all glyphs from GPU texture atlases (monochrome, color emoji, optional LCD antialiasing) into a vertex buffer and issues a single GPU draw call per frame; text is grouped into cacheable "words" with uniform SGR attributes, then split into shaping runs by script and emoji/text presentation. — [text stack](https://github.com/contour-terminal/contour/blob/master/docs/internals/text-stack.md)
- Contour requires OpenGL 3.3 (hardware or software rasterizer) and x86-64 with AES-NI or ARMv8 crypto; its GUI is Qt-based with native chrome, and it also uses GLFW3 for the input path in the (possibly older) internals doc. — [README](https://github.com/contour-terminal/contour/blob/master/README.md); [internals index](https://github.com/contour-terminal/contour/blob/master/docs/internals/index.md)
- notcurses is a TUI library, not an emulator: it abandons X/Open Curses, uses terminfo for capabilities, and writes escapes to a terminal; its core abstraction is a z-buffer of `ncplane` framebuffers, with a split between `ncpile_render()` (virtual screen) and `ncpile_rasterize()` (physical screen), plus `ncpile_render_to_buffer()` for buffer-based drawing. — [README](https://github.com/dankamongmen/notcurses/blob/master/README.md); [USAGE](https://github.com/dankamongmen/notcurses/blob/master/USAGE.md)
- Oxterm is a GTK3/VTE application: `gtk = 0.18`, `pango`, `cairo-rs`, `zoha-vte = 0.6` with feature `v0_70`, and `zoha-vte-sys` only for `vte_terminal_get_text_range()`; display-free logic is already separated into `src/headless/`. — [Cargo.toml](/home/andres/Progetti/oxterm/Cargo.toml); [headless/mod.rs](/home/andres/Progetti/oxterm/src/headless/mod.rs)

### Inferences
- The reusable pattern is *state/core separate from rendering*: Contour's `vtbackend`/`vtrasterizer` and Rio's `librio`/`libsugarloaf` allow headless tests, alternate frontends and embedding. Oxterm's `src/headless/` boundary already follows this idea for non-display logic; extending it to VT/protocol parsing would be the natural place for new protocol features.
- GPU rendering buys atlas caching, single-draw-call frames and shader effects, but it is not what enables search, command blocks or hyperlinks — those are state/metadata features. Oxterm can adopt most of the latter without touching VTE's renderer.
- A GTK3/VTE app can still borrow the *rendering discipline* (dirty-row tracking, per-change damage, cached shaped runs) only at the chrome/overlay level; inside the VTE widget, damage and text shaping belong to VTE.

### Gaps
- WezTerm docs state front-end choices but do not publicly detail its glyph atlas/shader pipeline; no performance comparison between its `OpenGL`, `WebGpu` and `Software` paths was found.
- Rio's changelog documents latency work but no absolute GPU-vs-CPU benchmark numbers were found.
- No confirmed feature matrix for VTE 0.70 (ligatures, OSC 8, grapheme clustering) was fetched; VTE-specific feasibility claims below are therefore conservative.

## 2. Which specific features are noteworthy (images, ligatures, Unicode, hyperlinks, scrollback search, split rendering, multiplexing, mouse/keyboard, shaders, TUI widgets)?

### Takeaway
The most transferable ideas are metadata over scrollback (command blocks, marks, folding, sticky headers), explicit input/protocol hardening (paste protection, keyboard encodings, focus per pane), and latency/damage engineering. The most visually impressive ideas (inline images, glyph protocol, custom shaping, GPU shaders) are renderer-owned and out of reach without replacing VTE.

### Cited Findings
- WezTerm features: ligatures, color emoji and font fallback, true color and dynamic color schemes; hyperlinks; searchable scrollback; xterm-style selection with bracketed paste; SGR mouse reporting; many render attributes (underline, double underline, italic, bold, strikethrough); tabs, splits, multiple windows, SSH + serial ports. — [Features](https://wezterm.org/features.html)
- WezTerm scrollback search has four selectable match modes (case-sensitive, case-insensitive, "smart" = case-sensitive only if query has uppercase, regex), live match count, highlight-all and navigation by match/page; saved searches can be configured. Scrollback size is a configurable line bound, and the scrollbar can be disabled/enabled. — [Scrollback](https://wezterm.org/scrollback.html)
- WezTerm has Quick Select and a Vi-like Copy Mode with "semantic zones" (moving by semantic zone type), and hyperlink rules mix OSC 8 with regex-detected URLs. — [features](https://wezterm.org/features.html); [KeyAssignment reference](https://wezterm.org/config/lua/keyassignment/index.html)
- WezTerm supports the iTerm2 inline image protocol plus a built-in `imgcat`, with a `doNotMoveCursor=1` extension; kitty graphics and experimental sixel are listed in features. Its docs explicitly note image protocols are not fully handled in multiplexer sessions. — [imgcat](https://wezterm.org/imgcat.html); [features](https://wezterm.org/features.html)
- Rio's headline protocol work is the *Glyph Protocol* (spec v1.18): programs register SVG-path/`vg`/COLRv1 glyphs in a reserved 1024-codepoint PUA-B block, queries can ask whether a whole grapheme cluster renders, registrations bind at print time so later re-registration does not repaint the screen, and fonts/rasterization (tiny-skia) use bounded viewBoxes, payload caps and memory budgets. — [CHANGELOG 0.6.0 entries](https://github.com/raphamorim/rio/blob/main/CHANGELOG.md)
- Rio implements full kitty keyboard protocol including shift/modified keys and associated text, `modifyOtherKeys` levels 1/2 with xterm-style `CSI 27;m;...~` for Enter/Tab/Backspace, numpad handling, per-pane focus reports (`CSI ? 1004 h`), OSC 8 links with verbatim URIs, OSC 9;4 animated progress bars, OSC 133 shell integration and command-finish notifications, OSC 7501 program status, vi mode/hint navigation/search, and synchronized output. — [CHANGELOG](https://github.com/raphamorim/rio/blob/main/CHANGELOG.md)
- Rio's latency/damage engineering is concrete: keystrokes are written on the wakeup that delivers them, query replies are written by the parsing thread rather than the UI thread, the PTY reader releases the terminal lock every ≤64 KiB chunk, search/hover/cursor changes rebuild only rows that changed, and there are `cargo bench -p rio-vt --bench vt_frame` and a PTY latency example. Paste protection rejects dangerous control bytes and asks before unbracketed multi-line pastes. — [CHANGELOG](https://github.com/raphamorim/rio/blob/main/CHANGELOG.md)
- Contour's command blocks turn OSC 133 (and OSC 3008) shell integration into first-class scrollback objects: exit-status rail, folding, line numbers (absolute/relative/hybrid), timestamps, scrollbar marks, sticky command header, finish notifications, per-block menus, "copy command line safe to paste", pager opening, and relative paths resolved against the command's own cwd; up to 1000 block records are kept by default even after output scrolls away. — [Command blocks guide](https://contour-terminal.org/demo/command-blocks/)
- Contour also has hint mode (URLs, paths, git hashes), vi-like input modes and line marks, read-only mode, buffer capture VT extension, Sixel + kitty graphics (with Unicode placeholders used by Claude Code for Mermaid diagrams) and ReGIS; text reflow is configurable via `SM ? 2028` and synchronized rendering via `SM ? 2026`. — [Features](https://contour-terminal.org/features/); [README](https://github.com/contour-terminal/contour/blob/master/README.md)
- Contour's synchronized-output doc explains the tearing problem, `CSI ? 2026 h/l` (BSU/ESU), DECRQM-based feature detection, and notes VTE/gnome-terminal does **not** support it, while notcurses, foot, kitty, iTerm2, WezTerm, mintty and Contour do. — [Synchronized output](https://contour-terminal.org/vt-extensions/synchronized-output/)
- Contour exposes a typed control API/CLI (`ls`, `new`, `split`, `send`, `pane capture`, `block read`), an MCP server for coding agents, tmux control-mode gateway in both directions, sandboxed WebAssembly status-line extensions, layouts and drag-and-drop pane/tab rearrangement. — [README](https://github.com/contour-terminal/contour/blob/master/README.md); [features](https://contour-terminal.org/features/)
- notcurses provides a z-buffer of planes with z-order, transparency, resize callbacks, alignment and scrolling; blitters degrade from pixel protocols (Sixel, kitty, Linux framebuffer) to Unicode sextants/octants/quadrants/Braille; widgets include reels, plots, progbars, tabs and readers; it supports kitty's keyboard protocol and capability probing (terminfo, `TERM`, `COLORTERM`, `notcurses_check_pixel_support`). — [USAGE](https://github.com/dankamongmen/notcurses/blob/master/USAGE.md); [README](https://github.com/dankamongmen/notcurses/blob/master/README.md)
- notcurses' "rendered mode" computes an optimized byte stream from a virtual screen and `ncpile_render_to_buffer()` can hand that buffer to the caller; its README explicitly argues against rendering everything to bitmaps (slow, inflexible, poor mouse selection, limited Sixel palettes). — [README](https://github.com/dankamongmen/notcurses/blob/master/README.md); [USAGE](https://github.com/dankamongmen/notcurses/blob/master/USAGE.md)

### Inferences
- The strongest "cheap wins" for Oxterm are scrollback metadata UX (marks, folding, sticky header, search modes) and input hardening (paste safety, keyboard encodings, focus state). These are GUI/state features, not renderer features.
- Damage tracking and lock-hold discipline are ideas worth applying to *Oxterm's own* UI updates (overlay redraws, search highlight changes), even if VTE owns the grid.
- VTE's lack of synchronized output (per Contour's adoption table) means apps that emit `CSI ? 2026 h` will tear in Oxterm; there is no GTK-side fix without VTE support or a PTY proxy.
- Inline images, custom glyph registration, reflow and full control of ligature shaping are fundamentally renderer features: a GTK overlay can show a *thumbnail or separate image view*, but cannot place images inside VTE's character grid.

### Gaps
- No reliable source was found on whether VTE 0.70 already renders OSC 8 hyperlinks or supports ligatures via Pango; verify against the installed VTE before planning hyperlink/hint features.
- No screenshots were inspected directly; visual claims are from project docs/README descriptions.
- WezTerm shader effects were not confirmed from a primary doc page; only the presence of GPU frontends and appearance/background customization was verified.

## 3. Which ideas are feasible for a GTK3/VTE-based app and which require a different rendering stack?

### Takeaway
Feasible now: search UX, scrollback metadata overlays (marks, line numbers, folding chips, sticky header, notifications), paste/keyboard hardening, hints, control CLI and headless protocol parsing. Needs a headless/PTY-layer implementation: sequences VTE does not surface (OSC 9;4, 777, 7501, kitty keyboard, synchronized output). Needs a VTE replacement or a parallel renderer: inline images, reflow, glyph protocol, true text-shaping control, GPU shaders and multiplexed screen mirroring.

### Cited Findings
- Oxterm already implements VTE-backed scrollback search (regex/case flags, match highlighting, result navigation) in [scrollback.rs](/home/andres/Progetti/oxterm/src/terminal/scrollback.rs:38), plus OSC 133 prompt navigation, vi copy mode, hints and a history picker ([scrollback.rs](/home/andres/Progetti/oxterm/src/terminal/scrollback.rs), [vi_copy.rs](/home/andres/Progetti/oxterm/src/terminal/vi_copy.rs), [hints.rs](/home/andres/Progetti/oxterm/src/terminal/hints.rs), [history_picker.rs](/home/andres/Progetti/oxterm/src/terminal/history_picker.rs)). A headless OSC 133 module and CLI/control plumbing already exist ([osc133.rs](/home/andres/Progetti/oxterm/src/headless/osc133.rs), [control_cli.rs](/home/andres/Progetti/oxterm/src/headless/control_cli.rs)). 
- Oxterm already has a headless layer with themes, settings spec, remote/connection logic and MCP/agent support, which is the right home for protocol-level ideas that must stay display-free ([headless/mod.rs](/home/andres/Progetti/oxterm/src/headless/mod.rs), [spec.rs](/home/andres/Progetti/oxterm/src/headless/spec.rs), [mcp.rs](/home/andres/Progetti/oxterm/src/headless/mcp.rs)).
- **GTK/VTE-feasible (UI layer only):** WezTerm-style match modes and saved searches and a live match count (extend the existing VTE `VteRegex` search); Contour-style gutter marks, scrollbar marks and sticky header drawn as a fixed-width column/`GtkOverlay` on top of the VTE widget; command blocks derived from the OSC 133 marks Oxterm already parses, persisted in its existing SQLite store; finish notifications via desktop notifications; Rio-style paste confirmation and control-byte sanitization in the input path; hint rules extended to git hashes/paths with command-cwd resolution.
- **Headless/protocol-level (not visible to VTE):** intercepting and acting on OSC 9;4 progress, OSC 777/9 notifications, OSC 7501 program status, kitty keyboard encoding and focus reports requires seeing the byte stream; VTE 0.70 exposes a limited API (Oxterm already needs `zoha-vte-sys` for text extraction), so a PTY proxy/filter or a VTE with OSC event signals would be needed. Synchronized-output (2026) acknowledgement also belongs here, and VTE is listed as unsupported ([Synchronized output adoption table](https://contour-terminal.org/vt-extensions/synchronized-output/)).
- **Different rendering stack required:** sixel/kitty/iTerm2 images *inside* the grid ([WezTerm imgcat](https://wezterm.org/imgcat.html), [Contour images](https://contour-terminal.org/features/)); Rio's glyph protocol and per-cell custom glyph rasterization ([CHANGELOG](https://github.com/raphamorim/rio/blob/main/CHANGELOG.md)); Contour's word cache, shaping runs and GPU atlas ([text stack](https://github.com/contour-terminal/contour/blob/master/docs/internals/text-stack.md)); text reflow and multiplexer screen mirroring with native scrollback ([features](https://contour-terminal.org/features/), [multiplexing](https://wezterm.org/multiplexing.html)).
- notcurses' *ideas* (plane compositing, diffed render buffer, capability-based degradation) are transferable as design patterns to GTK overlays/status bars, but its implementation is a client library that emits escapes; it cannot add pixels to a VTE widget ([README](https://github.com/dankamongmen/notcurses/blob/master/README.md), [USAGE](https://github.com/dankamongmen/notcurses/blob/master/USAGE.md)).

### Inferences
- The cheapest high-value path is to keep VTE and build a "scrollback intelligence" layer on top: OSC 133 → command blocks → marks/folding/sticky header/notifications, plus the existing search and hint machinery. This mirrors Contour's most distinctive feature set without any renderer change.
- The next tier is protocol interception in `src/headless/`: Oxterm can parse progress/status sequences from a wrapped PTY even if VTE ignores them, then display them in GTK chrome. This preserves the headless boundary test.
- Anything requiring per-cell pixels or control over shaping is a VTE replacement decision; a hybrid (VTE for grid + separate GTK layer for images) would not give true inline placement.

### Gaps
- No source confirms whether VTE offers OSC event callbacks in the version Oxterm uses; this determines whether the protocol tier needs a PTY proxy.
- No compatibility study of a VTE → Rio/Contour core swap was found; migration cost is unknown.
- The exact GTK overlay approach for a gutter (avoids resizing the VTE widget mid-command, as Contour does) was not prototyped here.

## 4. What are the trade-offs and costs (complexity, dependencies, portability)?

### Takeaway
GPU stacks, multiple frontends, protocol extensions and daemon multiplexing all buy polish or latency but add explicit build, testing and portability burdens; for Oxterm, incremental GTK overlays and headless protocol parsing have a far better cost/benefit ratio than replacing VTE.

### Cited Findings
- WezTerm's multiple frontends and the brief WebGpu default flip followed by a revert illustrate driver/portability risk; it keeps a CPU fallback and auto-selects it on Windows Remote Desktop. Its multiplexer docs label the feature "young" and evolving, and its image docs note incomplete support in mux sessions. — [front_end](https://wezterm.org/config/lua/config/front_end.html); [multiplexing](https://wezterm.org/multiplexing.html); [imgcat](https://wezterm.org/imgcat.html)
- Rio's cost profile: 15 workspace crates, MSRV 1.100.0, `wgpu` 30, a build-time GLSL→SPIR-V compiler on Linux, a separate native Metal path on macOS, and a very large, actively hardened protocol surface (glyph protocol revisions, payload caps, FIFO/`dev/shm` validation, notification escaping, paste safety). Benefit: headless `librio` and `libsugarloaf` C ABIs let other apps embed terminal state and rendering, and there are dedicated benchmarks for frame and latency paths. — [Cargo.toml](https://github.com/raphamorim/rio/blob/main/Cargo.toml); [sugarloaf README](https://github.com/raphamorim/rio/blob/main/sugarloaf/README.md); [libsugarloaf README](https://github.com/raphamorim/rio/blob/main/libsugarloaf/README.md); [CHANGELOG](https://github.com/raphamorim/rio/blob/main/CHANGELOG.md)
- Contour's cost profile: C++23, Qt6, vcpkg on Windows, CMake presets, OpenGL ≥3.3, CPU crypto requirements, and a daemon with protocol version negotiation across releases; it mitigates with explicit latency budgets (≤+10 ms launch, ≤+1 ms keystroke median vs in-process) and a CI trend job. Measurements show the daemon costs about +0.34 ms startup and ~+9 µs idle keystroke p50 (16/20 pairs worse), while bulk throughput stays ~340 MiB/s. — [README](https://github.com/contour-terminal/contour/blob/master/README.md); [latency doc](https://github.com/contour-terminal/contour/blob/master/docs/internals/latency.md)
- notcurses' cost profile: terminfo 6.1+, libunistring, optional libgpm/QR/FFmpeg/OpenImageIO; a core-only build (`-DUSE_MULTIMEDIA=none`, `notcurses-core`) removes the heavy dependencies; it refuses to start with a bad `TERM`, and direct mode is documented as substantially slower and less capable than rendered mode. — [README](https://github.com/dankamongmen/notcurses/blob/master/README.md); [USAGE](https://github.com/dankamongmen/notcurses/blob/master/USAGE.md)
- Oxterm's current dependency set is comparatively lean (GTK3, Pango, Cairo, VTE 0.70, SQLite, regex, nix/libc) and its release profile already uses LTO, single codegen unit and panic=abort. — [Cargo.toml](/home/andres/Progetti/oxterm/Cargo.toml)

### Inferences
- Adding a WebGPU/OpenGL renderer would mean new shader toolchains, GPU-driver fallbacks and a second text stack — a large, high-risk change for a GTK3 app whose widget tree and selection model are VTE/Pango-based.
- Daemon-style persistence is also expensive: Contour needs latency gates and protocol versioning even for a thin client. Oxterm's existing remote/connection workspace code may deliver similar value with less new machinery.
- Capability probing is a cheap, high-value habit from notcurses: probe before emitting optional sequences, degrade gracefully, and keep a "core" path with minimal dependencies.
- Oxterm can copy the *measurement discipline* (Rio's frame/latency benches, Contour's latency budget) for any new overlay/search work without adopting GPU rendering.

### Gaps
- No person-month or dependency-count estimates for a VTE replacement were found.
- No direct benchmark comparing GTK/VTE rendering with these GPU stacks was found; claims about relative speed are not quantified here.
- The maintenance cost of keeping protocol extensions in sync with upstream specs (glyph protocol, kitty keyboard) is described in Rio's changelog but not quantified.
