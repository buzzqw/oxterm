# Security and secret-handling lessons from seven modern terminal/agent projects for Oxterm

Scope: cross-cutting security/secret handling only (credential storage, import/export, consent/RCE models, incidents). Projects: r-shell, Orca, Omnix, Motty, Electerm, Tabby, Waveterm. Oxterm baseline assumed from the brief: connections book with **no secrets**, OS Secret Service/keyring for passwords, an import path that never reads secrets, and a headless control API.

## Key Question 1 — How do these projects store credentials, SSH keys, tokens, and connection data (OS keychain vs encrypted files)?

### Takeaway
Two clear patterns emerge: (a) native-keychain-backed secret stores (Waveterm, Orca, Motty, Electerm's current wrapper) where the connection/config file holds only a *reference* to the secret, and (b) passphrase-encrypted vaults (Tabby, R-Shell sync, Motty's own vault) where encryption is application-level and key derivation or device keys matter. Oxterm's "no secrets in the book + OS keyring" design matches the strongest pattern, but several projects show that the *fallback* path (no keychain, portable copy, sync export) is where confidentiality usually breaks.

### Cited Findings
- **Waveterm** stores passwords/API keys/tokens encrypted in its config directory with the encryption key protected by the OS secure credential store: macOS Keychain, Windows Credential Manager, or Linux Secret Service. `connections.json` holds only a secret *name* (`ssh:passwordsecretname`), not the password; on Linux, no compatible keyring means secrets cannot be set and a warning is shown. — [Secrets docs](https://docs.waveterm.dev/secrets); [Connections docs](https://docs.waveterm.dev/connections)
- **Waveterm** connection data itself (host/user/port/identity paths/init scripts) lives in readable `connections.json` and it parses `~/.ssh/config`; identity files stay as filesystem paths. — [Connections docs](https://docs.waveterm.dev/connections)
- **Motty** stores saved passwords and key passphrases in an **AES-256-GCM vault keyed by the system secret store**, with an explicit fallback: "key file beside the vault where there is none (and in a portable copy)" — and the README warns "anyone who can copy that folder can read the vault." AI provider keys and TOTP/HOTP seeds are in the vault too. — [Motty README, Security section](https://github.com/t8y2/motty/blob/main/README.md)
- **Motty** verifies host keys against its own `known_hosts` *before* credentials are sent; supports agent keys, identity files, OpenSSH user certificates, `.ppk` (Argon2id), PKCS#11-style security keys via agent, and per-host restriction of offered agent keys (`IdentitiesOnly`-like). — [Motty README, Hosts and authentication](https://github.com/t8y2/motty/blob/main/README.md)
- **Tabby** uses a passphrase-encrypted "vault" (not the OS keychain): PBKDF2-SHA512, 100,000 iterations, random 8-byte salt, random 16-byte IV, **AES-256-CBC**, base64 ciphertext stored in config YAML; no authentication tag in the stored format. When enabled, the *entire config* (including SSH secrets) is encrypted into `store.vault` with `encrypted: true`. The passphrase can be remembered in memory for a configurable number of minutes; wrong passphrase offers retry/erase/quit. Private-key *file contents* can also be stored in the vault as base64 secrets addressed by `vault://<id>` URIs. — [vault.service.ts](https://github.com/Eugeny/tabby/blob/master/tabby-core/src/services/vault.service.ts); [config.service.ts](https://github.com/Eugeny/tabby/blob/master/tabby-core/src/services/config.service.ts)
- **Tabby README** describes an "integrated encrypted container for SSH secrets and configuration"; a community plugin (`ssh-keymap`) lets synced SSH profiles reference private keys by name using a **local mapping file that is never synced** — evidence that absolute key paths in synced config are a known portability/privacy problem. — [Tabby README](https://github.com/Eugeny/tabby/blob/master/README.md)
- **Electerm** now wraps Electron `safeStorage` (macOS Keychain, Windows DPAPI, Linux libsecret/gnome-keyring) via `safeEncrypt`/`safeDecrypt`, but **returns the original plaintext unchanged if safeStorage is unavailable**; it persists a random 32-byte storage key in `storage-key.enc` encrypted by that same wrapper. Its sync/export encryption moved from legacy AES-192-CBC with a zero IV and constant `'salt'` to AES-256-GCM with random IV/salt and an auth tag, while retaining legacy decryption. — [safe-storage.js](https://github.com/electerm/electerm/blob/master/src/app/lib/safe-storage.js); [storage-key.js](https://github.com/electerm/electerm/blob/master/src/app/lib/storage-key.js); [enc.js](https://github.com/electerm/electerm/blob/master/src/app/lib/enc.js)
- **R-Shell** keeps connection profiles as editable JSON with private keys as *local file references*; remembered SSH key passphrases are encrypted with a device-local credential master key and stored separately from saved connections/source snapshots. Connection exports omit remembered passphrases and strip profile credentials, including nested jump credentials. — [OpenSSH import guide](https://github.com/GOODBOY008/r-shell/blob/main/docs/openssh-import.md)
- **Orca** stores Google/Composio sign-ins encrypted with the OS keychain; where no keychain exists, they are kept **unencrypted in a user-readable-only (0600) file**. For a web MCP server, saved headers/sign-ins are encrypted and injected by Orca so the bot never holds them; if there is no keychain, Orca refuses to save them. For a command-based MCP server, settings including keys in its environment are saved **unencrypted**, user-readable. — [Bot security docs](https://orca.dev/docs/bots/security)
- **Omnix** deliberately avoids holding provider tokens: agent profiles get isolated `CODEX_HOME`/`CLAUDE_CONFIG_DIR` folders and official CLI login flows, and the README states "Token tidak pernah dibaca atau disimpan" ("tokens are never read or stored"). State lives in `.omnix/` (SQLite FTS5 history, JSON state) and `~/.omnix/`. — [Omnix README](https://github.com/Zwart04/omnix/blob/master/README.md)
- **Waveterm** telemetry states it does not collect hostnames/IPs, keystrokes, file contents, AI prompts or commands; a separate daily diagnostics ping can be disabled with `WAVETERM_NOPING`. — [Telemetry docs](https://docs.waveterm.dev/telemetry)

### Inferences
- Oxterm's split (metadata in a plain book, secrets only in Secret Service) is the same separation Waveterm and Motty use, and is preferable to Tabby's whole-config encryption because metadata remains inspectable/mergeable without unlocking.
- The recurring weak point is the **fallback**: Motty's key-file-beside-vault, Electerm's plaintext-on-missing-safeStorage, Orca's 0600 file. Oxterm should decide explicitly what happens when the keyring is unavailable — fail closed for writes, or require an explicit user opt-in with a clearly labelled weaker mode.
- "Secrets redacted at source" is a design goal across Motty (terminal text before model calls) and Omnix (console/network redaction of `Authorization`, `Cookie`, `Bearer`, tokens/API keys/passwords in query strings); connection metadata alone can still be sensitive (host addresses, commands, notes) — R-Shell encrypts those too in its sync blob.

### Gaps
- No primary source was found describing Tabby's config-sync encryption format (what is encrypted with which key when syncing to Gist/WebDAV); only the local vault format was verified from source.
- No statement was found on whether R-Shell stores saved *SSH passwords* themselves in the OS keychain vs its device-local credential key; the docs describe "saved connection credentials" and "remembered passphrases" without naming a keychain backend.

## Key Question 2 — How do they import/export connections without leaking secrets?

### Takeaway
The strongest projects make import a **read-only, bounded, previewable operation with explicit consent per field**, and treat secrets as a separate opt-in category. The clearest counterexample is Electerm, which has a documented critical advisory for importing unsafe bookmark JSON that can lead to local code execution.

### Cited Findings
- **R-Shell's OpenSSH import** explicitly states: "Preview does not start SSH, execute a shell, read private keys, or connect to a server." It shows authentication, full jump chains, diagnostics and field diffs, selects only new clean hosts by default, and resolves conflicts with a per-field "Use source value" action. It bounds input: 4 MiB of distinct config files, 16 nested files, 4,096 aliases, 8 jump hosts, plus a 64 MiB work budget; exceeding it aborts the whole preview with no partial import. `Match`, `ProxyCommand`, custom host-key verification and unsupported auth providers block affected hosts rather than being silently converted. — [OpenSSH import guide](https://github.com/GOODBOY008/r-shell/blob/main/docs/openssh-import.md)
- **R-Shell** preserves locally stored credentials on re-import, keeps saved IDs/folders/notes/favorites, never deletes a connection when a source alias disappears, and leaves data intact on cancel/parse failure/corrupt storage. — [OpenSSH import guide](https://github.com/GOODBOY008/r-shell/blob/main/docs/openssh-import.md)
- **R-Shell cloud sync** encrypts a versioned full snapshot with Argon2id (64 MiB, 3 passes, 1 lane) + AES-256-GCM, fresh salt/nonce and a sync-specific authentication context; saved credentials are **off by default**, host addresses/commands/notes are encrypted, every device re-seals downloaded secrets under its own machine key, and private keys/paths/agent sockets/host trust/security switches stay local. A manual export with "Include passwords and other credentials" also carries storage-provider credentials encrypted with the export passphrase, but never the sync passphrase/history; import restores storage settings only on a device that has none. — [Cloud sync docs](https://github.com/GOODBOY008/r-shell/blob/main/docs/cloud-sync.md)
- **Motty imports** from OpenSSH config, PuTTY, Xshell, MobaXterm, WindTerm, **Electerm**, Netcatty, SecureCRT, FinalShell, Xterminal and XPipe; Electerm/Netcatty readable SSH passwords are imported **only with explicit consent** and re-import only fills missing passwords; SecureCRT/FinalShell/Xterminal/Xpipe store encrypted passwords so those imports carry connections only. — [Motty README](https://github.com/t8y2/motty/blob/main/README.md)
- **Motty backup/sync** uses an encrypted `.mottybak` export and record-level sync via WebDAV/S3/Gist/Gitee. Tabs, window layout, shortcuts, fonts, key paths, and cloud credentials stay local; remote WebDAV/S3 require HTTPS by default with an explicit "Allow insecure remote HTTP" warning, and WebDAV 302 redirects pass no credentials/cookies/referrer to another origin. — [Motty README](https://github.com/t8y2/motty/blob/main/README.md)
- **Motty settings-sync doc** (Chinese) lists synchronized categories including "credentials/keys" (saved passwords, private keys, passphrases) and trusted `known_hosts`, while stating sync-service passwords/tokens are never put into backups and GitHub Gist tokens are fetched on demand from `gh auth token` rather than stored. This is in tension with the README's "key paths stay local" statement: paths stay local, but key *contents* appear to be synchronized. — [settings-sync.md](https://github.com/t8y2/motty/blob/main/docs/settings-sync.md); [Motty README](https://github.com/t8y2/motty/blob/main/README.md)
- **Orca's bot import reader** refuses key, login, session and database files and drops lines that look like secrets; the importing bot is instructed to use only that reader, but Orca labels this "best effort", warns that a pasted reply is saved as-is, and asks the user to reconnect services instead of importing tokens. — [Bot security docs](https://orca.dev/docs/bots/security)
- **Electerm** syncs bookmarks to GitHub/Gitee secret gist/WebDAV/custom server/electerm cloud, and supports bookmark import — the combination is exactly what CVE-2026-45058 exploits (see Q5). — [Electerm README](https://github.com/electerm/electerm/blob/master/README.md); [GHSA-jgg9-rw32-44pj](https://github.com/advisories/GHSA-jgg9-rw32-44pj)
- **Tabby** config sync is a plugin (e.g. `sync-config` to Gist/Gitee); the `ssh-keymap` plugin's local, never-synced path mapping shows the ecosystem's workaround for key portability. — [Tabby README](https://github.com/Eugeny/tabby/blob/master/README.md)

### Inferences
- Oxterm's "import never reads secrets" is the right invariant and matches R-Shell's strongest claim; it should be asserted in tests (no keyring or private-key file access during import) and documented so users trust the boundary.
- Avoid importing *executable configuration* (commands, `ProxyCommand`, arbitrary env) even when it comes from a trusted-looking file. Electerm's import advisory and Motty's "volunteer passwords only with explicit consent" show that imported data must be treated as untrusted input, not as configuration.
- For sync/export, follow R-Shell's pattern: default-off credential inclusion, separate passphrase from provider credentials, AEAD with random salt/nonce and a context label, and never downgrade to a "weaker validator" when a server misbehaves.

### Gaps
- No detailed public import/export spec was found for Omnix, Waveterm or Tabby beyond the README/docs mentions above; whether their connection imports parse secret-bearing fields was not verified.

## Key Question 3 — Security warnings, sandboxing, remote code execution, and consent models

### Takeaway
Every agent-capable project in this set separates "can read" from "can act" with an explicit gate, and most state plainly that the gate is **not a sandbox**. Omnix and Motty are the most explicit about layered controls (allowlists, default-off servers, approval gates, no kernel sandbox); Orca has the richest consent documentation and simultaneously warns that prompt injection can defeat instruction-based rules.

### Cited Findings
- **Motty**: "The approval gate is a safety control, not a sandbox. Do not point an agent at a host where a wrong command is unacceptable." Its MCP server is **off by default, loopback-only, bearer-token protected**; hosts must be explicitly opened to agents; `list_hosts` lists only authorized hosts and omits unauthorized ones; sudo for remote files is off by default, never elevates the terminal, and passwords are held only for the connection. — [Motty README](https://github.com/t8y2/motty/blob/main/README.md)
- **Motty** highlights secrets redaction before terminal text reaches a model (key files, assignments, URL credentials, token formats), provider keys in the vault, and an assistant risk classification with approval gate; a stdio MCP variant has no port/token and works only on hosts opened to agents. — [Motty README](https://github.com/t8y2/motty/blob/main/README.md)
- **Omnix**: plugins are native programs verified by SHA-256 with revocable permissions and stdio JSON-RPC invoked on demand; installation never runs them; **no kernel sandbox**, so install only trusted sources; dev builds install over the running binary only after owner approval. Browser tools deny non-http(s) schemes, gate `evaluate` behind `--allow-eval` with event logging, support a per-workspace host allowlist, import cookies only for the exact requested domain after a confirmation dialog to a 0600 file, and tell agents that page text is data, not instructions. — [Omnix README](https://github.com/Zwart04/omnix/blob/master/README.md); [docs/browser.md](https://github.com/Zwart04/omnix/blob/master/docs/browser.md)
- **Orca** defaults new bot conversations to **Full access** (agents run commands/edit files without asking) unless the chat permission is changed; it recommends "Ask for approval" for bots reachable by other people or reading mail/issues/messages, notes that some agents have no approval mode and always run full access, and warns "None of these settings is a guarantee." Enforced controls: `Who can ask` checked in Orca Cloud before requests reach the machine; scheduled look-around is read-only; memory tidy-up has no tools; bots cannot create bots without a human clicking Create bot. Instruction-only rules include never merging PRs unless asked, drafting mail instead of sending, treating external content as information, and never saving secrets to memory. Anyone in `Who can ask` acts with **the owner's access**; event automations and webhooks bypass that list, and webhooks should use a signing secret. — [Bot security docs](https://orca.dev/docs/bots/security)
- **Orca** keeps bot soul/memory as plain Markdown users can review; code work lands in worktrees and PRs; turning bots off stops new runs but leaves data. Remote servers pair via generated links (typically over Tailscale) or `orca serve --pairing-address`; SSH worktrees and per-workspace cloud VMs use machines/accounts the user controls. — [Bot security docs](https://orca.dev/docs/bots/security); [Ways to run](https://orca.dev/docs/ways-to-run)
- **Waveterm** installs a `wsh` helper on remote hosts at `~/.waveterm/bin/wsh` and requires `AllowTcpForwarding`; `conn:askbeforewshinstall` defaults to true (prompt before install) but can be set false to auto-install. It supports user-defined `cmd:env` and initialization scripts per connection. — [Connections docs](https://docs.waveterm.dev/connections)
- **R-Shell** warns that VNC uses an unencrypted RFB connection and should be tunneled over SSH on untrusted networks; macOS builds are ad-hoc signed; backend commands for cloud sync are restricted to the main-window capability, never file-viewer popups; tests allow plain HTTP only to `127.0.0.1`, production requires HTTPS and certificate verification. — [R-Shell README](https://github.com/GOODBOY008/r-shell/blob/main/README.md); [Cloud sync docs](https://github.com/GOODBOY008/r-shell/blob/main/docs/cloud-sync.md)
- **Electerm**'s README documents deep links (`ssh://`, `telnet://`), global hotkeys, an MCP widget, AI agent mode, and "sync data including bookmarks" — the surface later targeted by several advisories. — [Electerm README](https://github.com/electerm/electerm/blob/master/README.md)

### Inferences
- Oxterm's headless control API is analogous to Motty's MCP and Omnix's CLI/browser tools: it should be default-off or explicitly enabled, loopback/stdio only, authenticated by a locally generated token, and restricted to an explicit allowlist of hosts/operations. "Approval gate, not sandbox" should be documented verbatim in the same spirit.
- Treat any remote-supplied string as untrusted: filenames, terminal hyperlinks, web page text, imported JSON. Electerm's CVE cluster shows how each of those became code execution.
- Prefer "deny by default + per-resource grant" (Motty hosts opened to agents; Omnix host allowlist) over "default full access with rules the model should follow" (Orca bots). If an Oxterm headless API can run commands, require an explicit per-host capability grant and log every request.
- Make downgrade paths visible: Omnix logs every allowed `evaluate` call, R-Shell refuses weak ETags, Motty warns before insecure HTTP. Silent fallbacks (Electerm safeStorage plaintext) are the dangerous kind.

### Gaps
- No primary source was found for a formal threat model or security policy in Omnix or R-Shell beyond the README/notes above; Orca and Motty have the most documented models.

## Key Question 4 — Concrete practices Oxterm should adopt or deliberately avoid

### Takeaway
Adopt: immutable preview imports, secret references in the book, OS keyring with fail-closed behavior, AEAD with random nonce/salt and context labels, per-capability headless API grants, redaction before any model/telemetry boundary, and documented "not a sandbox" warnings. Avoid: plaintext-on-fallback encryption, whole-config encryption that blocks metadata review, unvalidated deep links/shell.openExternal, imported executable fields, and silent insecure transport downgrades.

### Cited Findings
- Adopt R-Shell's import invariants ("preview does not start SSH, execute a shell, read private keys, or connect"), bounded parser budgets, `Match`/`ProxyCommand` blocking, and conflict-by-field reimport that preserves local credentials. — [OpenSSH import guide](https://github.com/GOODBOY008/r-shell/blob/main/docs/openssh-import.md)
- Adopt R-Shell's sync crypto: Argon2id + AES-256-GCM with fresh salt/nonce and domain-separated context, credentials off by default, per-device re-sealing, strong ETags/`If-Match` with 412 refresh, and refusal to accept weak validators. — [Cloud sync docs](https://github.com/GOODBOY008/r-shell/blob/main/docs/cloud-sync.md)
- Adopt Waveterm's reference model: connections store a secret *name*, OS backend chosen per platform, and a visible warning when no Linux Secret Service is available. — [Secrets docs](https://docs.waveterm.dev/secrets)
- Adopt Motty's explicit risk language and layered headless controls: off-by-default loopback bearer-token MCP, per-host agent authorization, redaction before model calls, and an explicit statement that approval is not a sandbox. — [Motty README](https://github.com/t8y2/motty/blob/main/README.md)
- Adopt Omnix's deny-by-default tool surface: scheme allowlist, `evaluate` gate with event log, host allowlist, exact-domain cookie import with confirmation and 0600 file, and telling agents that page content is data. — [docs/browser.md](https://github.com/Zwart04/omnix/blob/master/docs/browser.md)
- Adopt Orca's transparency about residual risk: document what is enforced vs merely instructed, and how to revoke access (remove people, disable connectors, rotate webhook keys, pause automations). — [Bot security docs](https://orca.dev/docs/bots/security)
- Avoid Electerm's patterns: deterministic CBC with fixed zero IV/constant salt and no MAC (CVE-2026-45787), passing entire `process.env` to the renderer (CVE-2026-43942), unvalidated `shell.openExternal` for terminal links (CVE-2026-43941), path traversal in widget loading (CVE-2026-43940), unsafe bookmark import/sync (CVE-2026-45058), single-instance socket as an unauthenticated local RPC channel (CVE-2026-45353), and shell-interpolated file paths (CVE-2026-49255). — [GHSA-g29v-q6h7-76wh](https://github.com/advisories/GHSA-g29v-q6h7-76wh); [GHSA-37j4-88rp-2f6h](https://github.com/advisories/GHSA-37j4-88rp-2f6h); [GHSA-fwf6-j56g-m97c](https://github.com/advisories/GHSA-fwf6-j56g-m97c); [GHSA-f77v-9vpc-6pjm](https://github.com/advisories/GHSA-f77v-9vpc-6pjm); [GHSA-jgg9-rw32-44pj](https://github.com/advisories/GHSA-jgg9-rw32-44pj); [GHSA-7p5m-v798-f8vv](https://github.com/advisories/GHSA-7p5m-v798-f8vv); [GHSA-v5ff-xmfp-p245](https://github.com/advisories/GHSA-v5ff-xmfp-p245)
- Avoid Tabby's AES-256-CBC vault without a MAC if integrity of synced config matters; AEAD (GCM) is what Electerm migrated to after its advisory and what R-Shell/Motty use. — [vault.service.ts](https://github.com/Eugeny/tabby/blob/master/tabby-core/src/services/vault.service.ts); [enc.js](https://github.com/electerm/electerm/blob/master/src/app/lib/enc.js)
- Avoid silently degrading when the OS keystore is unavailable (Motty documents the risk; Electerm returns plaintext; Orca uses 0600). — [Motty README](https://github.com/t8y2/motty/blob/main/README.md); [safe-storage.js](https://github.com/electerm/electerm/blob/master/src/app/lib/safe-storage.js); [Bot security docs](https://orca.dev/docs/bots/security)

### Inferences
- A concrete Oxterm checklist: (1) add a boundary test asserting imports touch no keyring/key files; (2) document the headless API as loopback+token+allowlist, default-off; (3) audit every `openExternal`/URI scheme and every shell invocation of remote-controlled strings; (4) give any sync/export AEAD + random salt/nonce + explicit "include secrets" checkbox; (5) emit structured audit events for sensitive operations as Omnix does; (6) write the "approval is not a sandbox" line into the headless API docs.
- If Oxterm later adds an agent/AI feature, Motty's pre-model redaction and Orca's "external content is information, not instructions" rule are the minimum; Orca explicitly says model-followed rules cannot be forced.

### Gaps
- No project in this set publishes a full independent security audit of its headless/agent API that could be used as a ready-made checklist; this list is synthesized from docs, source and advisories.

## Key Question 5 — Notable incidents, security advisories, or documented design criticisms

### Takeaway
Electerm has a large, recent, publicly documented advisory cluster (including multiple critical unpatched issues); the other six projects had no GitHub Security Advisory hits in the queries performed, and none publish a prominent incident history. Criticisms that *are* documented are mostly design-level: Tabby's unauthenticated CBC vault, Electerm's plaintext fallbacks, Motty's portable key-file risk, Orca's full-access default, and Omnix's explicit "no kernel sandbox".

### Cited Findings
- **Electerm CVE-2026-45787** (GHSA-g29v-q6h7-76wh, medium, fixed 3.9.5): deterministic AES-192-CBC with fixed zero IV, constant KDF salt and no MAC for synced bookmark/profile data; attackers could crack common passwords across installs and flip ciphertext bits undetected. — [GHSA-g29v-q6h7-76wh](https://github.com/advisories/GHSA-g29v-q6h7-76wh)
- **Electerm CVE-2026-45353** (GHSA-7p5m-v798-f8vv, critical CVSS4 9.3, fixed 3.9.0): any same-user process could send JSON to the single-instance socket/pipe to create tabs and spawn attacker-controlled local processes without UI interaction. — [GHSA-7p5m-v798-f8vv](https://github.com/advisories/GHSA-7p5m-v798-f8vv)
- **Electerm CVE-2026-45058** (GHSA-jgg9-rw32-44pj, critical CVSS4 9.4, **no patch listed at advisory time**): importing unsafe bookmark JSON or a compromised sync target could inject `exec*` fields/global config causing local-PTY code execution when a bookmark is opened or sync applied. Workaround: do not import unsafe data. — [GHSA-jgg9-rw32-44pj](https://github.com/advisories/GHSA-jgg9-rw32-44pj)
- **Electerm CVE-2026-43944** (GHSA-mpm8-cx2p-626q, critical, fixed 3.8.8): arbitrary local code execution via crafted `electerm://` deep links, CLI `--opts`, or shortcuts; workarounds include unregistering the protocol handler. — [GHSA-mpm8-cx2p-626q](https://github.com/advisories/GHSA-mpm8-cx2p-626q)
- **Electerm CVE-2026-43943** (GHSA-q4p8-8j9m-8hxj, high, fixed 3.7.9): RCE via malicious remote filename in "open with system/custom editor". — [GHSA-q4p8-8j9m-8hxj](https://github.com/advisories/GHSA-q4p8-8j9m-8hxj)
- **Electerm CVE-2026-43942** (GHSA-37j4-88rp-2f6h, medium, **no patch listed**): the whole `process.env` (AWS/GitHub/LLM tokens etc.) is serialized to the renderer via IPC, readable by any renderer JS. — [GHSA-37j4-88rp-2f6h](https://github.com/advisories/GHSA-37j4-88rp-2f6h)
- **Electerm CVE-2026-43941** (GHSA-fwf6-j56g-m97c, high, **no patch listed at advisory time**): terminal hyperlinks are passed to `shell.openExternal` with no protocol validation; malicious terminal output can trigger dangerous protocol handlers on click. — [GHSA-fwf6-j56g-m97c](https://github.com/advisories/GHSA-fwf6-j56g-m97c)
- **Electerm CVE-2026-43940** (GHSA-f77v-9vpc-6pjm, critical CVSS3 9.8, fixed 3.7.16): `runWidget` path traversal exposed over IPC lets renderer JS load and execute arbitrary JS files. — [GHSA-f77v-9vpc-6pjm](https://github.com/advisories/GHSA-f77v-9vpc-6pjm)
- **Electerm CVE-2026-41501 / CVE-2026-41500** (GHSA-8x35-hph8-37hq, GHSA-wxw2-rwmh-vr8f, critical, fixed 3.3.8): command injection in npm installer `runLinux()`/`runMac()` via remote release metadata. — [GHSA-8x35-hph8-37hq](https://github.com/advisories/GHSA-8x35-hph8-37hq); [GHSA-wxw2-rwmh-vr8f](https://github.com/advisories/GHSA-wxw2-rwmh-vr8f)
- **Electerm CVE-2026-49255 / CVE-2026-49253** (GHSA-v5ff-xmfp-p245 high 8.8; GHSA-38j7-23hf-9mhc high 7.1, both fixed 3.11.11): shell command injection via SFTP filenames in `rmrf`/`mv`/`cp`, and Zmodem/Trzsz filename path traversal writing outside the chosen download directory. — [GHSA-v5ff-xmfp-p245](https://github.com/advisories/GHSA-v5ff-xmfp-p245); [GHSA-38j7-23hf-9mhc](https://github.com/advisories/GHSA-38j7-23hf-9mhc)
- **Tabby**: GitHub's advisory API query for the `tabby` package returned an empty list; the source-level criticism stands (AES-256-CBC with no MAC, whole-config encryption). — [GitHub advisories API query](https://api.github.com/advisories?affects=tabby); [vault.service.ts](https://github.com/Eugeny/tabby/blob/master/tabby-core/src/services/vault.service.ts)
- **Waveterm**: GitHub's advisory API query for `waveterm` returned an empty list; its docs claim no PII/command/prompt telemetry and offer opt-outs, but the diagnostics ping is separate and only disableable via env var. — [GitHub advisories API query](https://api.github.com/advisories?affects=waveterm); [Telemetry docs](https://docs.waveterm.dev/telemetry)
- **Orca** documents design criticisms rather than incidents: default Full access for bots, any added "Who can ask" user acts with owner access, event automations/webhooks bypass that list, some agents have no approval mode, and "a model can still be fooled" by prompt injection. — [Bot security docs](https://orca.dev/docs/bots/security)
- **Omnix** self-documents two risk disclosures: no kernel sandbox for native plugins, and a `--raw` MCP mode that bypasses the proxy's eval gate and allowlist ("should be regarded as a legacy path"). — [Omnix README](https://github.com/Zwart04/omnix/blob/master/README.md); [docs/browser.md](https://github.com/Zwart04/omnix/blob/master/docs/browser.md)
- **Motty** self-documents the portable/key-file fallback risk and directs vulnerability reports to GitHub private vulnerability reporting, asking users to keep credentials, hostnames and terminal output out of public issues. — [Motty README](https://github.com/t8y2/motty/blob/main/README.md)

### Inferences
- The advisory cluster shows a consistent theme: **untrusted input crossing a privilege boundary** (remote server -> local shell, web content -> renderer, import file -> config, URL -> OS handler, local IPC -> app actions). Oxterm's headless API is exactly such a boundary and deserves the same scrutiny.
- "No advisory found" is not evidence of no vulnerabilities: the search integration was unavailable (HTTP 402/429) and only GitHub's advisory DB was queried for the smaller projects; NVD/OSV/issue-trackers were not comprehensively searched.

### Gaps
- No advisories or public incidents were found for r-shell, Orca, Omnix, Motty, Tabby or Waveterm through GitHub advisory endpoints; this may be coverage bias rather than absence.
- No source was found confirming whether Electerm's unpatched advisories (43942, 43941, 45058) have since been fixed in releases after the advisory's `updated_at`; treat their patch status as "as stated in the advisory".
- Web search was unavailable during this research (HTTP 402/429), so issue discussions and third-party write-ups were not searched; findings rely on primary docs, source files and GitHub advisories.
