# Remote access, collaboration, mobile access and AI-assisted terminal workflows (r-shell, Omnix, Motty, Orca)

## 1. What does each project actually do, and what is its architecture?

### Takeaway
The four projects are not peers: r-shell and Motty are full multi-protocol desktop connection managers (closest to Oxterm), Orca is an agent IDE with a deliberately distributed runtime and a phone remote control, and Omnix is a small, explicitly local-first agent workbench that borrows three ideas from Orca. None of them is primarily a "remote shell server"; the closest thing is Orca's `orca serve` / managed server, which owns sessions so clients can attach.

### Cited Findings
- **r-shell** is a desktop app for SSH/SFTP/FTP/FTPS/RDP/VNC on macOS, Windows and Linux: "Split SSH terminals, edit remote files, and monitor multiple hosts in one desktop workspace." Its stack is Tauri 2 (OS webview, no bundled Chromium), a Rust backend using `russh`/`russh-sftp`, `suppaftp`, `tokio` and `tokio-tungstenite` for WebSocket PTY streaming, with a React 19 + TypeScript + xterm.js 6 frontend. The README explicitly calls the project "an experiment in AI-assisted development" — feature richness should not be read as independent validation. — [r-shell README](https://github.com/GOODBOY008/r-shell/blob/main/README.md)
- r-shell's remote-access surface includes: connection manager with folders/favorites/tags and drag-and-drop, OpenSSH config import with jump chains, SSH tunnels via jump hosts, JSON import/export, Chrome-style lazy session restore, recent-connection Quick Connect, exponential-backoff auto-reconnect (up to 5 attempts), and detached sessions with keep-alive that can be reattached (`Cmd/Ctrl+Shift+H`). — [r-shell README](https://github.com/GOODBOY008/r-shell/blob/main/README.md)
- r-shell's PTY is browser-side xterm.js streamed over a local WebSocket with bounded flow control; terminal search, WebGL renderer with canvas fallback, IME/CJK input, working-directory follow for the remote file browser, and recursive grid split panes are documented. VNC is RFB 3.3/3.7/3.8 over TCP and unencrypted; the README recommends tunneling it over SSH. RDP supports tab or native-window display and bounded dirty-rectangle frame delivery. — [r-shell README](https://github.com/GOODBOY008/r-shell/blob/main/README.md)
- **Motty** is a desktop SSH client written in Go on the Viva framework (Metal/Direct3D/Vulkan), with "no Electron runtime, no embedded browser and no JavaScript layer". It owns SSH, authentication, SFTP, terminal emulation, forwarding, remote-desktop protocols, persistence and product workflows; Viva owns windowing, input, layout, components and rendering. Source layout: `cmd/motty` (entry point, headless mode, MCP bridge, `mcp-serve`), `internal/sshconn`, `internal/term`, `internal/rfb`/`internal/desktop/vnc`, `internal/rdpcore`/`internal/desktop/rdp`, `internal/sftpclient`/`internal/scpclient`, `internal/forward`, `internal/workbench`, `internal/ai`. — [Motty README](https://github.com/t8y2/motty/blob/main/README.md)
- Motty's terminal, hosts, files and monitors share one window: real PTYs with 256/true colour, alternate screen, 5,000-line scrollback, kitty keyboard protocol, synchronized updates (DECSET 2026), image protocols (Kitty/iTerm2/SIXEL), split panes that can be moved between windows and restored without reconnecting, plus a resource monitor and server-log panel. — [Motty README](https://github.com/t8y2/motty/blob/main/README.md)
- Motty supports Mosh as an optional transport for an SSH host, so a terminal survives Wi-Fi/hotspot/VPN changes and predicts typing on slow links; its docs explicitly list what a Mosh session does **not** carry. It also supports sudo-enabled SFTP (privileged file operations) that never elevates the terminal, with passwords held only for the connection. — [Motty README](https://github.com/t8y2/motty/blob/main/README.md)
- **Orca** is an open-source agent IDE: "Bots inside your agent IDE." Bots in Slack/Linear/GitHub run the user's own Claude Code or Codex on the user's machine and return tested PRs; the desktop supports Chat UI or raw CLI for the same conversation, agent orchestration with workers in separate worktrees, split panes, git review, and a CLI that can create worktrees/start workers/drive browsers/schedule automations. Supported agents list is large (Claude Code, Codex, OpenCode, Copilot, Cline, etc.), and the README says any terminal CLI agent works. — [Orca README](https://github.com/stablyai/orca/blob/main/README.md)
- Orca has four documented run modes: local desktop; **SSH targets** (worktree, agents and git worktree run remotely, editor/diff/UI stay local; Orca installs a managed server on the host on first connect); **Remote Orca Server** (a machine running Orca desktop or `orca serve` owns projects, worktrees, terminals and agent processes; clients are UI only); and per-workspace cloud VMs from repo recipes (`orca.yaml`, BYO provider). Orca does not sell managed hosting. — [Orca ways to run](https://orca.dev/docs/ways-to-run); [Orca README](https://github.com/stablyai/orca/blob/main/README.md)
- Orca's SSH details: built-in client checks effective OpenSSH `known_hosts`, defaults to first-contact trust with fingerprint display, rejects changed keys before prompting for credentials, supports keyboard-interactive/MFA, and falls back to system `ssh` for GSSAPI/Kerberos and FIDO2/security-key identities. Reconnect restores attached tabs with scrollback, size and full-screen frames, buffers keystrokes typed while disconnected, and keeps agents alive because PTYs live on the host's managed server. A Ports panel detects listening ports on the workspace host, forwards them with one click, auto-remaps privileged ports, and persists saved forwards across reconnects/restarts. — [Orca SSH worktrees](https://orca.dev/docs/ssh)
- Orca's **mobile companion** is an iOS/Android app that pairs with a desktop (one-time code, device token, optional Relay or LAN path); it is explicitly a remote control, "not a full editor". It shows agents/worktrees across connected hosts, hydrates recent terminal scrollback, offers Chat UI or terminal per session, sends replies/approvals, runs saved Quick Commands, does small source-control operations, and receives push notifications. Both the mobile companion and Remote Orca Servers are labelled **beta**. — [Orca mobile](https://orca.dev/docs/mobile); [Orca remote servers](https://orca.dev/docs/remote-servers)
- **Omnix** is a small Rust desktop workbench (GitHub repo created 2026-11-16, 0 stars at research time, GPL-3.0) that "takes the three most useful ideas from Orca — indexed history, sleep/resume worktree, handoff — and throws away the rest": one window, local-first, plugins only when invoked, no Electron/React, no account, no cloud, no background daemon. README is in Indonesian; docs include an English plugin API doc. — [Omnix repo metadata](https://api.github.com/repos/Zwart04/omnix); [Omnix README](https://github.com/Zwart04/omnix/blob/master/README.md)
- Omnix architecture: all durable state in `.omnix/` (SQLite FTS5 history index with `sessions`/`messages`/`messages_fts`, `workspaces.json` keyed by canonical path and `pane_key`, handoff receipts `.json` + brief `.md`, git worktrees, cooperative lease JSON files with PID/TTL/owner, per-terminal Lightpanda browser sessions). Modules: `src/history.rs`, `workspace.rs`, `handoff.rs`, `agent.rs`, `browser.rs`. It has two browser engines (native WebView for humans, headless Lightpanda for agents) behind one tool contract. — [Omnix architecture](https://github.com/Zwart04/omnix/blob/master/docs/architecture.md); [Omnix README](https://github.com/Zwart04/omnix/blob/master/README.md)
- Omnix's handoff receipts use an honest state machine `journaled | handed-to-terminal | not-delivered | unconfirmed`: if the agent spawn dies mid-way, the old honest record stays, and an unproven prompt is never claimed as delivered. Worktree/branch/port leases are cooperative, with dead/expired leases cleaned on read, no background monitor. Per-terminal browser sessions mean `browser stop` only closes the caller's session. — [Omnix architecture](https://github.com/Zwart04/omnix/blob/master/docs/architecture.md); [Omnix README](https://github.com/Zwart04/omnix/blob/master/README.md)
- Omnix explicitly lists unbuilt surfaces: headless screenshots (`Page.captureScreenshot` is a placeholder), a full CDP client, and a public plugin catalog (returns 404 until published). It also says Linux is fully built/tested, Windows is cross-compiled but untested on real Windows, macOS CI-built but unrun. — [Omnix README](https://github.com/Zwart04/omnix/blob/master/README.md)
- Omnix's roadmap says a future remote/daemon mode would add a per-`(host, session_id)` session lease fence — i.e. remote/shared sessions are a **planned** idea, not a feature. — [Omnix architecture](https://github.com/Zwart04/omnix/blob/master/docs/architecture.md)

### Inferences
- The closest architectural analogue to Oxterm is Motty (single-user desktop terminal that owns SSH, tunnels, SFTP and an AI/MCP bridge) albeit in Go with a custom rendering framework; r-shell is the closest *feature checklist* (same protocol set, dashboards, logs, sync) but with a webview/xterm.js frontend.
- Orca's key architectural lesson is separation of runtime from UI: "session sharing" is achieved by moving PTY/agent state onto a server and letting laptop/web/phone attach, not by sharing a local terminal widget.
- Omnix is too small and too local-first to be a remote-access model, but its receipt state machine and cooperative leases are directly reusable ideas for command-execution reliability.
- Maturity labels: r-shell's features are broadly documented but self-reported and the README calls the project an experiment; Motty publishes explicit limitation docs; Orca labels remote servers and mobile beta; Omnix labels several surfaces unbuilt and its desktop/web tests as self-tests. None of these claims were independently benchmarked here.

### Gaps
- No source code of r-shell, Motty or Orca was inspected; architecture statements come from READMEs/docs and may lag the code. GitHub API metadata for Omnix was checked, not its commit history in detail.
- No architecture diagram for r-shell or Motty was found in the fetched READMEs; Motty's MCP protocol details beyond the README are in its website docs (`motty.page/en/docs`), not fetched.
- It is not documented whether r-shell or Motty support any form of live multi-user terminal sharing; absence in README/docs is not proof of absence in code.

## 2. Which features are transferable to a desktop terminal (connection book, tunnels/jump hosts, session sharing, web/mobile access, command-execution APIs, audit trails)?

### Takeaway
The most transferable items are concrete and small: OpenSSH-config-aware connection books with per-hop jump authentication, loopback-only saved tunnels tied to a tab's lifetime, explicit host allow-lists for agent-driven command APIs, background-job start/poll/stop, and honest outcome receipts. Web/mobile access is transferable only as an architecture pattern (remote runtime + pairing tokens), not as a feature you can bolt onto a local GTK terminal.

### Cited Findings
- **Connection book design.** r-shell offers a tree sidebar with folders, favorites, tags, drag-and-drop ordering, editable saved profiles, JSON import/export and OpenSSH import that previews hosts *and jump chains* from `~/.ssh/config`. — [r-shell README](https://github.com/GOODBOY008/r-shell/blob/main/README.md)
- Motty imports hosts from OpenSSH config, PuTTY, Xshell, MobaXterm, WindTerm, Electerm, Netcatty, SecureCRT, FinalShell, Xterminal and XPipe; it groups/tags/colours hosts, verifies host keys before sending credentials, and retains per-host `ServerAliveInterval`, `ServerAliveCountMax`, `IdentitiesOnly` and identity files on OpenSSH import/sync. — [Motty README](https://github.com/t8y2/motty/blob/main/README.md)
- Orca's SSH target form adds an OpenSSH config picker (including `Include`d files), a **Test** button before Save, "In Orca" badges, and Advanced Connection options for proxy, jump host and multiplexing; connection reuse is on by default and can be disabled for hosts that reject multiplexed sessions. — [Orca SSH worktrees](https://orca.dev/docs/ssh)
- **Tunnels and jump hosts.** Motty's local, remote, SOCKS5 and HTTP CONNECT rules bind to loopback by default, are persisted, start explicitly, and stop with the SSH tab that owns them; jump routes authenticate each hop independently; a global outbound SOCKS5/HTTP proxy can carry the initial connection, or per-host settings can force direct, use a custom proxy, or use `ProxyCommand` such as `cloudflared access ssh`. VNC/RDP can ride an SSH host when the server only listens on loopback. — [Motty README](https://github.com/t8y2/motty/blob/main/README.md)
- Orca's Ports panel detects listening ports on the workspace host (excluding other users' ports on shared Linux hosts), forwards with one click, auto-remaps privileged remote ports locally, and persists forwards across reconnects and restarts. — [Orca SSH worktrees](https://orca.dev/docs/ssh)
- **Session sharing / multi-client.** Orca Remote Server keeps full session state on the server; multiple paired clients (laptop, web, mobile, automation) can share the runtime, while a sidebar filter can "Hide other-client workspaces" so one device only lists its own. Reconnecting returns to the server-owned workspace/tab/visible-pane state without duplicating paired tabs. — [Orca remote servers](https://orca.dev/docs/remote-servers)
- Orca explicitly distinguishes SSH worktrees (laptop owns runtime; agents keep running on host on disconnect; one laptop drives the host) from Remote Orca Server (remote machine owns full runtime; laptop/web/mobile/automation share it). — [Orca ways to run](https://orca.dev/docs/ways-to-run)
- **Web/mobile access.** Orca mobile is a thin client for terminal scrollback, replies, approvals, Quick Commands and source control; Host address can be edited to `IP`, `host:port`, `ws://` or `wss://` without re-pairing, and pairing can use LAN or Orca Relay. — [Orca mobile](https://orca.dev/docs/mobile)
- Motty instead targets network roaming at the *session* layer (Mosh), which keeps a SSH terminal alive across Wi-Fi/hotspot/VPN changes; its docs list the features a Mosh session does not carry. — [Motty README](https://github.com/t8y2/motty/blob/main/README.md)
- **Command execution APIs.** Motty has an optional MCP server off by default, loopback-only and bearer-token protected, plus `motty mcp-serve` over stdio for an agent with no port/token that works only on hosts explicitly opened to agents. Both offer background jobs: `terminal_start` returns a job id immediately, `terminal_poll` reads output by offset, `terminal_stop` ends the command; `list_hosts` returns stable host IDs/names/addresses for authorized hosts and omits unauthorized hosts. In windowed HTTP MCP, `list_sessions` lists only open terminals with different session IDs; in stdio mode it lists authorized hosts by host ID. — [Motty README](https://github.com/t8y2/motty/blob/main/README.md)
- Orca's CLI exposes worktree creation, worker start, browser/desktop driving and scheduled automations to agents; bots can be triggered from Slack/Linear/GitHub/webhooks and a bot's worker runs in its own git worktree, reaching the repo through a branch and PR. — [Orca README](https://github.com/stablyai/orca/blob/main/README.md); [Orca bot security](https://orca.dev/docs/bots/security)
- Omnix's CLI offers `history index/search`, `agent track/sleep/resume`, `handoff`, `browser fetch/serve/stop/mcp`, `lock acquire/list/release`, and its plugin API 1 contributes `command|agent|browser-tool|hook|panel` over stdio JSON-RPC invoked on demand. — [Omnix README](https://github.com/Zwart04/omnix/blob/master/README.md)
- **Audit trails.** Orca keeps every bot chat (including automation/event runs) in history, gives each automation a run history and each webhook a call list, and stamps `asked by <name> via <bot>` into Linear comments/Gmail drafts/calendar descriptions/Docs comments when someone other than the owner asked. — [Orca bot security](https://orca.dev/docs/bots/security)
- Omnix indexes agent transcripts (including `role='tool'`) in SQLite FTS5 with phrase→AND→OR→prefix fallback, but deliberately excludes tool output from search results because it is useful for identifier lookup but dangerous as an "answer"; source hash of the first 8 messages detects forks. — [Omnix architecture](https://github.com/Zwart04/omnix/blob/master/docs/architecture.md)
- Motty supports explicitly recording a session, hides its AI capture wrapper/marker from screen and its own history (the remote shell's history is outside its control), and redacts key files, assignments, URL credentials and known token formats before terminal text reaches a model. — [Motty README](https://github.com/t8y2/motty/blob/main/README.md)
- r-shell's config sync keeps 90-day deletion tombstones and stable record IDs for three-way merges, but its README/docs do not describe a command audit log or tamper-evident session recording. — [r-shell cloud sync](https://github.com/GOODBOY008/r-shell/blob/main/docs/cloud-sync.md)
- **Config/book synchronization.** r-shell syncs encrypted full snapshots via WebDAV/S3 with Argon2id + AES-256-GCM, strong-ETag `If-Match` conditional writes, conflict review, credentials off by default, and local-only private keys/host trust/security switches. Motty syncs records via WebDAV/S3/Gist/Gitee with hybrid logical clocks and 90-day deletion tombstones; tabs, layout, shortcuts, fonts, key paths and cloud credentials stay local. — [r-shell cloud sync](https://github.com/GOODBOY008/r-shell/blob/main/docs/cloud-sync.md); [Motty README](https://github.com/t8y2/motty/blob/main/README.md)

### Inferences
- **High-value, low-risk shortlist for Oxterm:** (a) import `~/.ssh/config` including jump chains with a per-hop test/verify step, mirroring r-shell/Motty/Orca; (b) saved tunnels that are loopback-only, explicitly started, and owned by the connection tab; (c) a "Detected ports" panel that reuses the saved connection instead of asking for new credentials; (d) an agent-facing API that requires explicit per-host authorization and exposes start/poll/stop jobs, since Oxterm already has `send`/`wait`/`capture`/`events` as local primitives; (e) honest action receipts (`not-delivered`/`unconfirmed`/`delivered`) for any command sent on behalf of an agent; (f) redaction of terminal text before any model call. — [r-shell README](https://github.com/GOODBOY008/r-shell/blob/main/README.md); [Motty README](https://github.com/t8y2/motty/blob/main/README.md); [Orca SSH worktrees](https://orca.dev/docs/ssh); [Omnix architecture](https://github.com/Zwart04/omnix/blob/master/docs/architecture.md)
- **Medium-cost:** reconnect fidelity (scrollback replay, keystroke buffering, restored pane sizes) and config-book sync with tombstones/conditional writes. Both are well-specified in the cited docs but require persistence and merge machinery far beyond Oxterm's current local config. — [Orca SSH worktrees](https://orca.dev/docs/ssh); [r-shell cloud sync](https://github.com/GOODBOY008/r-shell/blob/main/docs/cloud-sync.md)
- **Not realistically transferable without a new server product:** phone/web access and multi-client session sharing. The only credible pattern in the cluster is Orca's: move the runtime to an always-on server, give each client a revocable token, and keep the phone as a thin controller. A GTK/VTE process with a per-user local socket cannot do this by extending its control API. — [Orca remote servers](https://orca.dev/docs/remote-servers); [Orca mobile](https://orca.dev/docs/mobile)
- No project in this cluster documents a dedicated SSH command audit trail with tamper evidence; the closest are Orca's bot/history/webhook logs, Motty's optional session recording and Omnix's handoff receipts. Treat a real audit trail as an open design problem, not a copyable feature. — [Orca bot security](https://orca.dev/docs/bots/security); [Motty README](https://github.com/t8y2/motty/blob/main/README.md); [Omnix architecture](https://github.com/Zwart04/omnix/blob/master/docs/architecture.md)

### Gaps
- No source-level detail on how Motty's `terminal_poll` offsets are defined or how its risk classification gates specific commands; the README describes behaviour but not the classification rules.
- No documentation found for session recording format, retention or integrity in Motty; no documentation found for audit-log retention in Orca.
- r-shell's docs do not state whether shared/collaborative sessions exist; Motty's docs do not describe a web client. These are treated as "not documented", not "impossible".

## 3. What security model do they use for authentication, secrets and multi-user access?

### Takeaway
All four are effectively single-user-at-the-keyboard products; multi-user access is a *delegation* layer (revocable tokens, "who can ask" lists, approval modes), not OS multi-user isolation. The strongest reusable patterns are: verify host key before credentials, keep secrets in an OS keychain/AES vault, make agent/MCP access opt-in and host-scoped, and treat approval gates as UX safeguards rather than sandboxes.

### Cited Findings
- **Host authentication.** Motty verifies host keys against its own `known_hosts` before any credential is sent; supports agent keys, identity files, OpenSSH user certificates (`@cert-authority`), PuTTY `.ppk` v2/v3 with Argon2id, passwords and keyboard-interactive rounds; hardware keys (`sk-ssh-ed25519`, `sk-ecdsa-sha2-nistp256`) go through OpenSSH's agent and `ssh-sk-helper` with a short-lived agent; agent forwarding is per-host and off by default. — [Motty README](https://github.com/t8y2/motty/blob/main/README.md)
- Orca checks built-in SSH connections against effective OpenSSH `known_hosts`; default policy accepts and remembers a host on first contact with fingerprint display, `StrictHostKeyChecking yes` rejects unknown hosts, and changed/revoked keys are rejected before password/passphrase prompts. GSSAPI/Kerberos and FIDO2 identities use system OpenSSH rather than the built-in client. — [Orca SSH worktrees](https://orca.dev/docs/ssh)
- r-shell supports password, public key, SSH agent and keyboard-interactive SSH auth; its OpenSSH import previews jump chains. Its cloud-sync docs state that host trust, private keys and their paths, SSH agent paths, SSH config provenance, security switches and active sessions stay local. — [r-shell README](https://github.com/GOODBOY008/r-shell/blob/main/README.md); [r-shell cloud sync](https://github.com/GOODBOY008/r-shell/blob/main/docs/cloud-sync.md)
- **Secrets at rest.** Motty stores saved passwords/passphrases and TOTP/HOTP seeds in an AES-256-GCM vault under the host, with the vault key in the system secret store — or in a key file beside the vault where none exists, in which case "anyone who can copy that folder can read the vault". AI provider keys are in the vault; remote WebDAV/S3 sync requires HTTPS by default and HTTP is allowed only with an explicit insecure switch. — [Motty README](https://github.com/t8y2/motty/blob/main/README.md)
- r-shell sync snapshots are encrypted/authenticated with Argon2id (64 MiB, 3 passes, 1 lane) and AES-256-GCM with fresh salt/nonce and a sync-specific context; each device re-seals downloaded secrets under its own machine key. Credential sync is opt-in, and a local security setting that disables password saving also blocks credential transfer. — [r-shell cloud sync](https://github.com/GOODBOY008/r-shell/blob/main/docs/cloud-sync.md)
- Orca's bot secrets: Google/Composio sign-ins are keychain-encrypted (or `0600` without a keychain); web MCP headers/sign-ins are encrypted and injected by Orca so the bot never holds them; command-run MCP settings with keys in env vars are saved unencrypted but user-readable only. Bots are instructed never to save secrets in memory. — [Orca bot security](https://orca.dev/docs/bots/security)
- Omnix states that tokens are never read or stored (agent profiles get their own `CODEX_HOME`/`CLAUDE_CONFIG_DIR`); plugin installation never runs the plugin, permissions are revocable, SHA-256 is verified, and plugins get stdio JSON-RPC on invocation. It explicitly says there is **no kernel sandbox** — install only trusted plugins. — [Omnix README](https://github.com/Zwart04/omnix/blob/master/README.md)
- **Agent/API authorization.** Motty's assistant has an Ask mode (terminal as context) and an Agent mode (runs commands with risk classification and approval gate); switching modes on request can be remembered. Its MCP server is off by default, loopback-only and bearer-token protected; stdio `mcp-serve` has no port/token but only works on hosts explicitly opened to agents, and unauthorized hosts are omitted from both. — [Motty README](https://github.com/t8y2/motty/blob/main/README.md)
- Motty explicitly warns: "The approval gate is a safety control, not a sandbox. Do not point an agent at a host where a wrong command is unacceptable." — [Motty README](https://github.com/t8y2/motty/blob/main/README.md)
- **Multi-user/delegation.** Orca Remote Servers create a separate revocable token per paired client; each grant can be revoked, immediately disconnecting active clients; generating a new link replaces only the previous *unused* link. Docs instruct keeping the service on Tailscale/WireGuard/trusted LAN/SSH forwarding and never exposing the Orca port publicly. — [Orca remote servers](https://orca.dev/docs/remote-servers)
- Orca bots default to only the owner asking; added people use **the owner's** access and can start/steer/approve/stop the bot. Orca Cloud enforces "Who can ask" for Slack/GitHub/Linear requests; webhooks need a signing secret; unauthorised askers on Slack get a private note. Default chat permission is **Full access**, so a new bot starts there unless changed — the docs recommend "Ask for approval" for bots others can reach. — [Orca bot security](https://orca.dev/docs/bots/security)
- Orca treats external content as data, not instructions: import skips key/login/session/database files and redacts secret-looking lines (best effort), "look around" runs are read-only, memory tidy-up has no tools, and new bots require the owner to press Create. The docs concede a model can still be fooled. — [Orca bot security](https://orca.dev/docs/bots/security)
- Orca mobile pairing uses a one-time code establishing a per-device token; an unused QR/link expires after 10 minutes, and a pairing link grants access to the runtime and should be treated like a password. — [Orca mobile](https://orca.dev/docs/mobile); [Orca remote servers](https://orca.dev/docs/remote-servers)
- Oxterm's own control API follows the same local-only pattern: each GUI process publishes a private Unix socket, requests are length-prefixed JSON, peers are checked with `SO_PEERCRED`, and the API "never listens on a network socket". — [Oxterm source](file:///home/andres/Progetti/oxterm/src/control.rs)

### Inferences
- A coherent security story for an Oxterm agent feature would combine Motty's host allow-list and loopback/bearer MCP defaults with Orca's per-client revocable tokens and "who can ask" enforcement, while preserving Oxterm's existing `SO_PEERCRED` local socket as the privileged channel.
- Orca's "Full access by default" for bots is a cautionary example, not a model to copy: an agent-facing terminal API should default to read-only/ask-approval and require explicit opt-in for write/execute operations.
- Both Motty and r-shell treat credentials as the most sensitive synced data and keep key material/paths local; this aligns with Oxterm's headless/UI split and argues against putting secrets into any portable connection-book export without a separate passphrase.
- Omnix's "no kernel sandbox" caveat applies equally to any in-process extension mechanism for Oxterm: manifest permissions can express intent but do not contain a malicious extension.

### Gaps
- No project documents OS-level multi-user access to the *same* live terminal with per-user permission differences; "multi-user" here always means delegated requests running as the owner.
- Motty's exact risk-classification rules and Orca's permission-mode enforcement inside CLI agents are not specified in the cited docs.
- r-shell's README does not detail how its vault/machine key is protected at rest beyond the cloud-sync document's description; no independent security audit was found.

## 4. Which ideas would fit Oxterm's headless/control API, and which would not?

### Takeaway
Ideas that fit are those expressible as local, inspectable commands over Oxterm's existing JSON control socket and headless parser — explicit host authorization, job-style `start/poll/stop`, receipts, redaction, import/verify of connection books, and tab-owned tunnel lifecycle. Ideas that do not fit are those needing a network runtime, a second UI stack, or OS-sandbox guarantees: phone clients, Slack/GitHub bots, RDP/VNC viewers, browser engines, and in-process plugin ecosystems.

### Cited Findings
- Oxterm's scriptable API is `oxterm new|split|send|capture|wait|connect|connections|tunnel|events|action|workspace|mcp|browse|fix|agent`. It is a private per-user Unix socket with length-prefixed JSON and `SO_PEERCRED` checks; shells in a pane get `OXTERM_PANE`/`OXTERM_CONTROL` so in-pane tools can target their own pane. Parsing/help/`CliMode` live in `src/headless/control_cli.rs`, with GTK execution in `src/control.rs`. — [Oxterm control source](file:///home/andres/Progetti/oxterm/src/control.rs); [Oxterm CLI parser](file:///home/andres/Progetti/oxterm/src/headless/control_cli.rs)

### Inferences
- **Fits well:** (1) extend `connect`/`connections` with an OpenSSH-config import that previews hosts *and* jump chains and a per-host "test" verb, following r-shell/Orca; (2) add a per-host "expose to agents" flag and require it before `mcp`/`agent`/`send` from non-UI clients, as Motty does; (3) add job-style semantics (`send --job` returning an id, `wait`/`capture` by id, stop) to match Motty's background jobs and Omnix's honest receipts; (4) add redaction at the `capture` boundary for AI callers; (5) make tunnel ownership explicit in `tunnel list` output so a tab close stops its rules; (6) log control-API actions (op, pane, target host, outcome) to a local append-only file for a minimal audit trail. — [r-shell README](https://github.com/GOODBOY008/r-shell/blob/main/README.md); [Orca SSH worktrees](https://orca.dev/docs/ssh); [Motty README](https://github.com/t8y2/motty/blob/main/README.md); [Omnix architecture](https://github.com/Zwart04/omnix/blob/master/docs/architecture.md)
- **Fits with caution:** config-book sync (r-shell/Motty designs) would need the spec-generated options/settings path, machine key and conflict review; it is a large multi-device feature, not a small API addition. Orca-style reconnect fidelity is valuable but belongs to the remote-session layer, not the control parser. — [r-shell cloud sync](https://github.com/GOODBOY008/r-shell/blob/main/docs/cloud-sync.md); [Motty README](https://github.com/t8y2/motty/blob/main/README.md); [Orca SSH worktrees](https://orca.dev/docs/ssh); [Oxterm spec](file:///home/andres/Progetti/oxterm/src/headless/spec.rs)
- **Does not fit:** Orca bots/Slack/GitHub connectors, cloud relay, mobile app and per-workspace VMs require an always-on server, cloud service and a separate client stack; r-shell/Motty RDP/VNC viewers and browser/editor panels require UI subsystems beyond GTK3/VTE; Omnix's plugin runtime and Lightpanda browser need a plugin/CDP platform with sandbox caveats. — [Orca remote servers](https://orca.dev/docs/remote-servers); [Orca ways to run](https://orca.dev/docs/ways-to-run); [r-shell README](https://github.com/GOODBOY008/r-shell/blob/main/README.md); [Motty README](https://github.com/t8y2/motty/blob/main/README.md); [Omnix README](https://github.com/Zwart04/omnix/blob/master/README.md)
- The `SO_PEERCRED` local-socket boundary means any remote/mobile extension would have to introduce a new authenticated transport — a qualitative change, not a new CLI verb. Orca's pairing-token/revocation model is the pattern to follow if that product decision is ever made. — [Oxterm control source](file:///home/andres/Progetti/oxterm/src/control.rs); [Orca remote servers](https://orca.dev/docs/remote-servers)

### Gaps
- Oxterm's existing `mcp` implementation was not inspected in detail here, so this report does not claim how its tools are authorized today; the "add host allow-list" suggestion assumes it is not already host-scoped.
- No evaluation of how VTE's capture semantics would support Motty-style offset-based polling; this needs a code-level spike before committing to a job API.
- No cost/benefit estimate for implementing encrypted config sync in Oxterm's spec-generated settings system.
